[第 63 篇]({{< relref "cuda-kernel-opt-63-v4-fp4-ffn3" >}}) 用一条 1D `cp.async.bulk` 把 K2 的
权重 row-tile 搬进 smem，端到端做到 **B=64 4.487 ms / 90.0% 权重 roofline**。但那条曲线只画到
`B=64`。真正上线的 decode 服务，batch 往往是 128/256：把同一个二进制拉到 `B=256`，端到端
**6.468 ms**、权重 roofline 只剩 **62.1%**。

ROADMAP 给这轮留的假设是「`MTMAX=4` 的激活 smem 把 occupancy 压住了，试激活分片/流式复用」。
本篇把这句话证伪：**掉下去的不是 occupancy，是一份指令预算**。我们会看到：

- 把小 smem 几何（`BN=8`、3–4 CTA/SM）扫一遍，**全是负结果**——occupancy 不是墙；
- ncu 的顶层 pipe 是 **ALU 61%**、issue slots 68%、DRAM 只有 64%：**发射受限**；
- 整条 kernel 的指令可以拆成「**解码 ≈ 常数项 + `dp4a` ≈ 8·m 的线性项**」，解码从头到尾
  占 **59%（m=1）→ 43%（m=4）** 的指令；
- 把解码**整段短路**量天花板：`B=64` 只快 2.7%（DRAM 藏住了），`B=256` 快 **23%**——
  但即便解码免费，`B=256` 也只到 **77.8%**，剩下的洞是 `dp4a` 和发射口；
- 顺手修掉一个真 bug：`63` 的 TMA kernel 里 LUT **从来没初始化过**，所有 `DEC≠8` 的路径
  其实在算 0。这就是为什么我一度看到「LUT 快 1.37×」的幻影。

结论：**大 batch 的 FP4 decode FFN 已经不在带宽墙上，而在一张指令表上；下一个量级要动
张量核（IMMA）**。判据和数字都在下面。

## 一、先把「掉到哪」量清楚

shape 仍是 `/ssd/models/DeepSeek-V4-Pro/config.json` 的 routed expert FFN：
`hidden=7168`、`moe_inter=3072`、384 experts top-6、`expert_dtype=fp4`
（真实权重 `w1/w3 [3072,7168]`、`w2 [7168,3072]`，FP4 e2m1 + E8M0 block-32，见
[56 篇]({{< relref "cuda-kernel-opt-56-v4-fp4-moe" >}})）。权重铺满 384 专家 = **13.48 GB**，
roofline（把全部权重读一遍）**4.020 ms**。

同进程 `B=64/128/256`（`fp4_ffn4.cu`，`KTMA=1 EK=3 DEC=8`）：

| B | m=B/64 | K1 (ms / %HBM) | K2 (ms / %HBM) | sum (ms / %roof) | 端到端 (ms) | µs/token |
|---|---|---|---|---|---|---|
| 64  | 1 | 2.9250 / **91.6%** | 1.5224 / **88.0%** | 4.4650 / **90.0%** | 4.473 | 69.9 |
| 128 | 2 | 3.0487 / 87.9%     | 1.7037 / 78.7%     | 4.7799 / 84.1%     | 4.845 | 37.9 |
| 256 | 4 | 4.2325 / **63.3%** | 2.1757 / **61.6%** | 6.4683 / **62.1%** | 6.468 | 25.3 |

（`ffn_B64_128_256.out.txt`。`K1` = 合并的 `[w1;w3]` grouped GEMV，`K2` = `w2`。）

先注意一个反直觉的事实：**每 token 成本其实在下降**——从 `B=64` 的 69.9 µs/token 掉到
`B=256` 的 25.3 µs/token（**2.76×**）。大 batch 里权重被 4 个 token 共用，绝对时间只涨
1.45×，所以「62.1% 权重 roofline」这个指标**低估了它的效率**：它不是变慢了，只是工作的
性质从「搬权重」变成了「算 token」。真正的问题是：**那部分多出来的算力开销，能不能省。**

## 二、先证伪 roadmap 的 occupancy 假设

roadmap 猜的是 `MTMAX=4` 让激活 smem 涨到 `4×7168 B ≈ 28.7 KB`，加上权重 staging
`8 warps × 2 rows × 3584 B = 57.3 KB`，动态 smem **90.6 KB**，把 occupancy 从 `B=64` 的
3 CTA/SM 压到 **2 CTA/SM**（`ncu` 实测 `Theoretical Occupancy 25%`、`Block Limit Shared Mem 2`）。

如果这是墙，缩小 smem 就该变快。我们扫了一组几何（同一进程内 head-to-head，`bg` 模式）：

**K1（H=7168）**：

| 几何 (RWW,NW) | BN | smem | CTA/SM | B=128 (ms / %HBM) | B=256 (ms / %HBM) |
|---|---|---|---|---|---|
| **(2,8)** 现状 | 16 | 88–90 KB | 2 | **3.045 / 88.0%** | **4.199 / 63.8%** |
| (1,8) | 8 | 58 KB | 3–4 | 3.511 / 76.3% | 4.690 / 57.1% |
| (2,4) | 8 | 58 KB | 3–4 | 3.177 / 84.4% | 5.129 / 52.3% |

**K2（I=3072）**：

| 几何 (RWW,NW) | BN | smem | B=128 (ms / %HBM) | B=256 (ms / %HBM) |
|---|---|---|---|---|
| **(4,8)** | 32 | 57 KB | 4 | **1.680 / 80.0%** | 2.421 / 55.4% |
| **(4,4)** 现状 | 16 | 37 KB | 5–6 | 1.703 / 78.7% | **2.167 / 61.8%** |
| (2,8) | 16 | 31 KB | 5–6 | 1.768 / 75.8% | 2.912 / 46.0% |
| (8,8) | 64 | 108 KB | 2 | 1.836 / 73.0% | 3.462 / 38.7% |

（`bg_B128.out.txt`、`bg_B256.out.txt`。要点不是绝对值——这台共享 H100 的 run-to-run
抖动有 ~8%——而是**同一进程内的排序**：把 smem 从 90 KB 砍到 58 KB、CTA/SM 从 2 提到
3–4，**K1 反而更慢**；K2 也只有 `B=128` 的 `(4,8)` 比现状好 ~1.4%。）

**occupancy 不是墙。** 多出来的 CTA 只是在抢同一条发射口和同一批 ALU。

## 三、ncu：顶层 pipe 是 ALU，不是 DRAM

对 `B=256` 的 K1 跑 `--set full`（`ncu_b256_k1.out.txt`）：

```
DRAM Throughput               %   64.08      ← 只到 2/3
L2 Cache Throughput           %   66.46
Compute (SM) Throughput       %   67.58
Issue Slots Busy              %   67.58      ← 发射口 2/3 忙
No Eligible                   %   32.22      ← 1/3 的周期没有可发射 warp
Active Warps Per Scheduler  warp    3.86
ALU is the highest-utilized pipeline (61.2%)
Theoretical Occupancy 25% (Block Limit Shared Mem 2)
```

`Est. Speedup` 会把「uncoalesced global store」列得很高（Y 的标量写只占 4/32 B），但那个
流量极小；真正到顶的是 **ALU pipe（61.2%）** + 发射口（67.6%），而且 `No Eligible 32%`
说明 warp 不是没事干、是**在等依赖**——等 `dp4a`/`prmt` 的结果，或直接被发射口卡住。

一句话：**这是一条 instruction-issue-bound 的 kernel**，不是带宽 kernel。

## 四、解码方式全扫：PRMT 在所有 batch 都赢（附一个真 bug）

62 篇把解码从「每 nibble 一次 LDS 的 16 项表」换成整 16B chunk 的 `prmt` 位拼装后，K1 从
73.6% 到 83.4%。当时的笔记里留了一句「LUT 和 PRMT 的胜负取决于墙在哪一级」，于是这轮先把
`DEC=0`（256 项 `uint16`）/`DEC=4`（16 项）/`DEC=8`（PRMT）在三个 batch 上重新对一遍。

第一次跑出来的数字非常漂亮，也非常可疑：

```
#### B=256 DEC=0 ####   K1 3.0706 ms  82.5%   K2 1.8008 ms  61.8%   ← 当时看到的
```

比 `DEC=8` 的 4.21 ms 快 **1.37×**。但 check 一栏写着 `max_rel=0.000e+00 (ref~0.00)`——
参考值本身是 0，说明**整个输出是 0**。翻回 `63` 的 TMA kernel：

```cpp
// 63-v4-fp4-ffn3/fp4_ffn3.cu  gemv_fp4_tma
__shared__ uint16_t l16[1];          // ← 只有 1 个元素
const int tid = threadIdx.x;
(void)l16;                           // ← 从没 init 过
...
decode_word<DECODE>(wv[j], w8[2*j], w8[2*j+1], l16);   // ← 但 decode 在查它
```

`gemv_fp4`（cp.async 版）的 LUT 是对的（`l16[L16N<DECODE>()]` + `init_lut`），
**TMA 版却一直是 `l16[1]` 且未初始化**。所以 `63` 的 TMA 路径只有 `DEC=8`（不用 LUT）
是对的，任何 `DEC=0/4` 都在读越界/未初始化的 smem，输出全 0——**而那个「1.37×」就是把
解码换成了「读一个位置的垃圾、无 bank conflict」的假象**。

修法很小：把 TMA kernel 的 LUT 按 `L16N<DECODE>()` 申请并 `init_lut`（`fp4_ffn4.cu`）：

```cpp
__shared__ uint16_t l16[L16N<DECODE>()];
const int tid = threadIdx.x;
init_lut<DECODE>(l16, tid);
```

修完之后，真正的排序（同进程）：

| | B=64 K1 | B=128 K1 | B=256 K1 | B=64 K2 | B=256 K2 |
|---|---|---|---|---|---|
| DEC=0 256 项字节表 | 3.736 / 71.7% | — | 5.863 / 45.7% | 1.774 / 75.6% | 3.003 / 44.6% |
| DEC=4 16 项 nibble 表 | 3.323 / 80.7% | 3.653 / 73.4% | 5.174 / 51.8% | 1.705 / 78.6% | 2.548 / 52.6% |
| **DEC=8 PRMT（现状）** | **2.916 / 91.9%** | **3.045 / 88.0%** | **4.212 / 63.6%** | **1.509 / 88.8%** | **2.174 / 61.6%** |

**PRMT 在每一个 batch、每一个矩阵上都赢**，而且 batch 越大赢得越多（`B=256` K1：
`3.736→2.916` 是 LUT→PRMT 的 1.28×）。这符合 58/59/60 的教训：LUT 把成本从 ALU 换成
LDS，只有在「LSU 很闲、ALU 才是墙」且「表结构无冲突」时才划算；batch 越大、`dp4a` 越多，
ALU/LSU 都更紧，LUT 只会雪上加霜。

> 方法论：**对拍必须能抓住「输出全 0」**。这次的 check 之所以没拦住，是因为参考实现
> 用的是同一份 `hGU=0`，分母 `max(|ref|,1)=1`、分子 0，`max_rel=0` 反而「OK」。
> 修法是把 `ref~` 也打出来看——`ref~0.00` 就是红旗。已记进台账。

## 五、一份指令预算：解码 ≈ 常数项，`dp4a` ≈ 8·m

既然 occupancy 和 LUT 都排除了，就直接数指令。用
`sm__inst_executed_pipe_*` 取每个 pipe 的 warp 级指令数（`ncu_pipe_B64_B256.out.txt`）：

| kernel | total | ALU | FMA | LSU | ADU | DRAM% | SM% | occ% |
|---|---|---|---|---|---|---|---|---|
| K1 B=64  | 2.174e9 | **1.275e9** | 0.687e9 | 0.092e9 | 0.017e9 | 92.5 | 84.3 | 36.2 |
| K1 B=256 | 2.993e9 | **1.356e9** | 1.193e9 | 0.251e9 | 0.020e9 | 63.7 | 67.8 | 24.2 |
| K2 B=64  | 1.037e9 | **0.619e9** | 0.328e9 | 0.046e9 | 0.004e9 | 90.3 | 79.7 | 24.2 |
| K2 B=256 | 1.629e9 | **0.744e9** | 0.619e9 | 0.145e9 | 0.010e9 | 62.6 | 72.1 | 30.7 |

**关键信号：从 `m=1` 到 `m=4`，ALU 几乎不动（K1 1.275→1.356e9，+6%），FMA 涨 74%。**
这和数据结构完全一致：

- `prmt` 解码是**每个权重 chunk 一次**，与 token 数无关 → 记在 ALU，是**常数项**；
- `dp4a(w8[q], x8[mm][q])` 是**每个 (chunk, token) 一次**，`8` 条/chunk/token →
  记在 FMA，是 **8·m 的线性项**（外加每 chunk 的 int→float 折算）。

把 K1 的权重摊成「每 lane 每 16 B chunk」的 warp 单元（`8.98e9 B / 16 / 32 ≈ 1.754e7` 个
warp-chunk），可以拟合出每个 warp-chunk 的预算：

$$
\underbrace{\text{ALU}}_{\text{prmt 解码}} \approx 73 \quad(\text{与 } m \text{ 无关}),\qquad
\underbrace{\text{FMA}}_{\text{dp4a + 折算}} \approx 31 + 8m
$$

于是解码占全部指令的比例：

$$
f_\text{dec}(m)=\frac{73}{73+(31+8m)+\text{LSU/ADU}} \approx
\begin{cases}
0.59, & m=1\\
0.43, & m=4
\end{cases}
$$

这与第六节短路实测的收益方向完全对得上。**在 `B=64` 它是「隐藏成本」**（DRAM 92%，
ALU 在权重 DMA 后面跑得完）；**在 `B=256` 它变成了「显性成本」**（DRAM 只 64%，
ALU+FMA 把发射口占满）。

## 六、天花板实验：把解码整段短路

「怀疑某段是墙，就把它短路掉看天花板」是 42 篇用过的招。这里加一个 `DEC=99`：解码直接
`a = w; b = w`（结果无意义，只量时间）。

| | DEC=8 (ms / %HBM) | DEC=99 无解码 (ms / %HBM) | 解码价值 |
|---|---|---|---|
| K1 B=64  | 2.915 / 92.0% | 2.836 / 94.5% | **+2.7%**（DRAM 藏住） |
| K1 B=128 | 3.095 / 86.6% | 2.883 / 93.0% | **+7.4%** |
| K1 B=256 | 4.230 / 63.4% | 3.443 / **77.8%** | **+22.9%** |
| K2 B=64  | 1.521 / 88.1% | 1.432 / 93.6% | +6.2% |
| K2 B=128 | 1.697 / 79.0% | 1.461 / 91.7% | **+16.1%** |
| K2 B=256 | 2.171 / 61.7% | 2.185 / 61.3% | **−0.7%（无感）** |

（`decode_ceiling.out.txt`。）

两个结论：

1. **解码确实是一笔真金**：`B=256` K1 有 **23%** 的墙是 `prmt`，`B=128` K2 有 **16%**。
2. **但即使解码完全免费，`B=256` K1 也只能到 77.8%**，还差最后 22 个点——那就是
   `8m` 条 `dp4a` + 折算，以及发射口本身。同时 `B=256` 的 K2 对解码**完全没有反应**，
   说明它的墙在别处（`NITER=3` 太短、TMA 单级延迟，见第七节）。

也就是说，光优化解码最多把 `B=256` 端到端从 6.47 ms 推到约 5.6 ms（1.15×）；**要真正
追平 `B=64` 的 90%，必须把 `dp4a` 从 FMA pipe 上拿下来**。

## 七、K2 的特殊性：`NITER=3` 的短流水

K2（`w2 [7168,3072]`）在 `B=256` 对解码短路无感，值得单独看一眼。K2 每个 block 的
权重 tile 只有 `BN×(I/2)` 字节，`I=3072` 时 `NITER = I/1024 = 3`——**主循环只有 3 拍**。
TMA 是**单级**（issue、wait、算完结束），不像 `cp.async` 有多级软流水；3 拍的算量
盖不住一次 TMA 往返，于是 K2 的墙偏向「等 TMA 事件」而非「算」。这也解释了为什么
65 篇的几何扫描（`RWW/DEPTH/PIPE`）在 K2 上全负：**改 tile 补不了流水深度**。

对照实验（同进程）确认现状仍是最优：`B=256` K2 `(4,4)` 2.167 ms 胜过 `(4,8)` 2.421、
`(8,8)` 3.462、`(2,8)` 2.912（`bg_B256.out.txt`）。真正对 K2 有用的方向是**给 TMA 加
第二级缓冲**（smem 还塞得下），或把 `BN` 做大到 `NITER` 变长——留给下一篇。

## 八、正确的指标：tokens/ms，而不是 HBM%

把结论翻译成服务视角：

| B | 端到端 | µs/token | 权重 roofline | 真正的限制 |
|---|---|---|---|---|
| 64  | 4.473 ms | 69.9 | 90.0% | **HBM 带宽** |
| 128 | 4.845 ms | 37.9 | 84.1% | HBM + 解码开始显形 |
| 256 | 6.468 ms | 25.3 | 62.1% | **指令发射（ALU 43% / FMA 40%）** |

- `B=64`：DRAM 92%，加任何算力都没用；优化目标是**少搬字节**（已经 FP4 + E8M0，
  每个权重 0.531 B，接近理论下限）。
- `B≥128`：DRAM 掉到 64%，**加算力才有用**。此时 `62% HBM` 不代表实现差，只代表
  这条 kernel 被 `prmt + dp4a` 的指令表锁死。

## 九、下一站：把 `8m` 条 `dp4a` 交给张量核

预算已经指得很清楚：`B=256` K1 有 **40% 的指令是 FMA（`dp4a` + 折算）**。把它移到
tensor pipe（`mma.m16n8k32.s32.s8.u8.s32`，见 [48 篇]({{< relref "cuda-kernel-opt-48-w4a8-imma" >}})）
的账很直观：

- 短路解码给到 77.8%（3.44 ms），说明「decode 走 ALU」这条腿已经被量到底；
- `dp4a` 若也走 tensor，就只剩纯访存 + 少量 ALU，理论上回到 ~92% HBM（≈2.8 ms）；
- 代价是 `m=4` 要把 token 塞进 `n8` 的 N 维（浪费一半）或把 4 个 expert 的行拼成 M=16。

这正是 ROADMAP 第五/六部分要的「模型场景算子推到极致」：**当 decode 的指令预算已经被
`prmt` 压到极限、带宽也已经见底，剩下的唯一量级就是换数制/换流水线。**

## 小结

- **现象**：FP4 decode FFN 在 `B=64` 是 90.0% 权重 roofline，到 `B=256` 掉到 62.1%；
  但每 token 成本反而从 69.9 µs 降到 25.3 µs（2.76×）——它没变慢，是**瓶颈从带宽换成了发射**。
- **证伪**：roadmap 猜的 `MTMAX=4` 压 occupancy **不是原因**。缩小 smem（`BN=16→8`，
  CTA/SM 2→3/4）在 K1 上**全线更慢**，K2 只有 `B=128` 的 `(4,8)` 好 ~1.4%。
- **根因**：ncu 顶层 pipe 是 **ALU 61.2%**、issue slots 67.6%、DRAM 64%。指令预算
  `ALU≈73（常数，prmt）+ FMA≈31+8m（dp4a）`，解码占 **59%（m=1）→ 43%（m=4）**。
- **解码全扫（负结果 + 修 bug）**：PRMT(`DEC=8`) 在每个 batch 都赢 LUT；并修掉了 `63`
  的 TMA kernel LUT **从未初始化**的真 bug——此前看到的「LUT 快 1.37×」是输出全 0 的幻影。
- **天花板**：短路解码后 `B=256` K1 也只到 **77.8%**（+22.9%），说明剩下的洞是 `dp4a`；
  `B=256` K2 对解码无感（`NITER=3` 的 TMA 单级延迟是它的墙）。
- **判据**：DRAM% > 90% → 抠字节；DRAM% < 70% 且 ALU/Issue 高 → 抠指令；抠解码用 PRMT，
  抠 MAC 只能上张量核。

**下一篇**：把 K1 的 `dp4a` 换成 `mma.m16n8k32.s32.s8.u8.s32`（IMMA），用 `n8` 的 N 维
装最多 8 个 token，看能不能把 `B=256` 从 77.8% 的天花板推到 90%+。

（`fp4_ffn4.cu`、`ffn_B64_128_256.out.txt`、`decode_ceiling.out.txt`、
`bg_B128.out.txt`、`bg_B256.out.txt`、`ncu_b256_k1.out.txt`、`ncu_pipe_B64_B256.out.txt`）。
