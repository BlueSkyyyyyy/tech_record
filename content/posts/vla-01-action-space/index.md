VLA 的第一个工程决策不是选哪个 VLM，而是**动作怎么表示**。

这个选择会一路传导：表示决定了动作头的形式，动作头决定了推理步数，推理步数决定了 chunk 长度，chunk 长度决定了控制频率和延迟预算。选错了，后面每一个环节都在还债。

这一篇只回答四个问题：

1. 把每维动作切成 256 个 bin，到底损失了什么？
2. 为什么同样的表示在 3 Hz 的 RT-1 上够用，到 50 Hz 就崩？
3. FAST 的 DCT + BPE 省了多少 token，代价是什么？
4. chunk 长度为什么从 1 涨到 50，又为什么不能无限涨？

## 1. 动作长什么样

一个机械臂动作通常是一个向量：

- **关节空间**：7 维 = 6 个关节角 + 1 个夹爪开合；双臂 14 维；人形可以到 132 维（GR00T N1.7 的 `max_action_dim=132`）。
- **末端空间**：7 维 = 位置 $(x,y,z)$ + 旋转（欧拉角/四元数/6D）+ 夹爪。
- **表示方式**：绝对位置、相对当前状态的偏移（relative）、相邻两步的差分（delta）。

这三种表示在误差累积上完全不同。UMI 的对比很直观：relative 的每个动作都回指**同一个当前状态**，新一次推理可以干净地重置参照系；delta 的每一步依赖上一步，误差会累积；absolute 需要一致的全局坐标系。

LeRobot 的文档把这件事写得很清楚，并且注明 π0/π0.5/π0-FAST 默认在归一化**之前**做 relative 转换（`docs/source/action_representations.mdx`）。这不是风格问题：归一化看到的是 delta 值，统计量必须按 delta 重新算，否则 q01/q99 会对不上。

## 2. 256 个 bin 的真相

RT-1、RT-2、OpenVLA 都把每维动作离散成 256 个 bin。OpenVLA 的实现只有几十行：

```python
# prismatic/vla/action_tokenizer.py:31-36
self.bins = np.linspace(min_action, max_action, self.n_bins)
self.bin_centers = (self.bins[:-1] + self.bins[1:]) / 2.0
self.action_token_begin_idx = int(self.tokenizer.vocab_size - (self.n_bins + 1))
```

注意第一行：`np.linspace(-1, 1, 256)` 产生的是 **256 条边界**，不是 256 个档位。中心点 `(bins[:-1]+bins[1:])/2` 只有 **255 个**。所以所谓「256 bins」的有效档位是 255，步长 $2/255 \approx 0.00784$，最大量化误差是半格 $1/255 \approx 0.00392$。

`code/vla/action_binning.py` 把这件事算了出来：

```
== 1. 分箱口径 ==
边界数=256 中心数=255 步长=0.007843
理论最大误差=0.003922 (半格)
实测最大误差=0.003922  RMS=0.002264
```

### 2.1 小动作幅度的相对误差

绝对误差看起来很小（0.4% 满量程），但对**小幅度动作**不是：

```
      动作范围      绝对误差(max)       相对范围
±1.00            0.003922     0.20%
±0.50            0.003922     0.39%
±0.10            0.003921     1.96%
±0.02            0.003921     9.80%
```

精密装配、插拔、拧螺丝这类任务，关节增量常在 ±0.02 rad 量级，9.8% 的相对误差已经超过很多任务的容差。这不是「模型不够大」，是**均匀分箱的分辨率在小动作区间不够**。

更糟的是误差会累积。如果动作是 delta 表示，50 步 chunk 的最坏累积误差是 $50 \times 0.00392 = 0.196$，RMS 约 $\sqrt{50/3} \times 0.00392 = 0.016$：

```
步数= 10  最坏累积=0.0392  RMS 累积=0.0072
步数= 25  最坏累积=0.0980  RMS 累积=0.0113
步数= 50  最坏累积=0.1961  RMS 累积=0.0160
```

### 2.2 一个容易被忽略的不一致

OpenVLA 的 bin 边界是 256 条（255 档），但 π0.5 把 state 塞进 prompt 时用的是：

```python
# openpi/models/tokenizer.py:24-27
discretized_state = np.digitize(state, bins=np.linspace(-1, 1, 256 + 1)[:-1]) - 1
```

`np.linspace(-1, 1, 257)[:-1]` 是 **256 条边界**，`digitize` 后减 1 得到 **0..255 共 256 档**。也就是说：OpenVLA 的 action 是 255 档，π0.5 的 state 是 256 档。两个数字都叫「256 bins」，含义不同。写论文/博客时把这两个混用，误差分析就对不上。

> **类比的边界**：256 个 bin 像把一把 1 米的尺子分成 255 格，每格约 3.9 mm。量桌子够用，量螺丝的螺纹就不够。而且这把尺子的刻度是**均匀**的，不会在常用区间自动加密——除非你改用分位数分箱或可学习的 tokenizer。

## 3. 频率：为什么 50 Hz 会杀死离散 token

FAST 论文给了一个很准确的判断（p.4）：动作 token 的边际信息随控制频率升高趋近于零。

算一笔账。50 Hz 下，1 秒有 50 个动作；相邻两帧的关节角差通常远小于 1°。如果每维每步一个 token，一个 1 秒的 14 维双臂 chunk 就是：

$$
50 \times 14 = 700 \text{ 个 token}
$$

而一段 700 token 的文本，信息量可能是几百个词；700 个动作 token 的信息量，可能只相当于十几个「关键帧」。自回归模型在这种序列上学到的最省力的策略，就是**复制上一个 token**。

FAST 的压缩率（Table I, p.7）说明了差距：

| 数据集 | 维度/频率 | naive token | FAST token | 压缩比 |
|---|---|---|---|---|
| BridgeV2 | 7 维 / 5 Hz | 35 | 20 | 1.75× |
| DROID | 7 维 / 15 Hz | 105 | 29 | 3.6× |
| Bussing | 7 维 / 20 Hz | 140 | 28 | 5.0× |
| Shirt Fold | 14 维 / 50 Hz | 700 | 53 | 13.2× |

FAST 的做法是：按维做 1%–99% 分位归一化 → **DCT** → 乘 scale $\gamma=10$ 后量化 → 低频优先、跨维交错展平 → **BPE**（词表 1024）压缩。`code/vla/action_binning.py` 里有一个只做 DCT + 均匀量化的玩具版，能看出能量集中有多强：

```
    每维保留      总系数       RMSE       最大误差      压缩比
      50      350    0.00389    0.01566    1.00x
      25      175    0.00389    0.01566    2.00x
      15      105    0.00512    0.03020    3.33x
      10       70    0.00969    0.07151    5.00x
       5       35    0.02974    0.21895   10.00x
       2       14    0.28536    0.80468   25.00x
```

一段 50 步 × 7 维的平滑轨迹，**保留一半低频系数，RMSE 和全保留完全一样**——因为高频系数本来就是 0。这就是 DCT 的价值：把「时间上的冗余」变成「频域上的零」，再用 BPE 把连续的零压成一个 token。

代价在推理侧：π0-FAST 每个 chunk 要自回归解码 **30–60 个 token**，在 4090 上约 **750 ms/chunk**；而 diffusion π0 只要 **10 步去噪、约 100 ms/chunk**（FAST p.9）。FAST 用 7.5 倍的推理时间，换来了训练时 5× 更少的 GPU hours 和高频任务的可训练性。**它解决的是训练效率，不是推理效率。**

## 4. chunk：从 1 步到 50 步，再到 100 步

动作表示的第二个维度是时间粒度。

ACT 最早把 chunk 做成核心设计：每 $k$ 步观测一次，生成接下来 $k$ 个动作，顺序执行。它的消融非常残酷（p.9–10）：

- $k=1$：成功率 **1%**
- $k=100$：**44%**
- $k=200/400$：回落

也就是说，**没有 chunk，ACT 在精细任务上几乎不可用**。原因不是模型 capacity，而是单步预测没有足够的时间上下文，且每次推理的微小误差都会立刻反馈到下一步。

后来的模型把 chunk 推得更长：

| 模型 | chunk | 控制频率 | 推理/执行 |
|---|---|---|---|
| RT-1 / RT-2 / OpenVLA | 1 | 3–6 Hz | 每步推理 |
| ACT | 100 | 50 Hz | 每 100 步推理 |
| Diffusion Policy | $T_a=8$（常用） | 10 Hz | 每 8 步重规划 |
| Octo | 未定（ALOHA 微调 64/执行 12） | 5–15 Hz | receding horizon |
| π0 | **50** | 50 Hz | 每 0.5 s 推理，执行 25 步 |
| π0.5 | 50（论文写 H=49） | 50 Hz | 10 步去噪 |
| OpenVLA-OFT | 8（LIBERO）/ 25（ALOHA） | 25 Hz | 整块开环 |
| RDT-1B | $T_a=64$ | 6 Hz（chunk/s） | 64 步动作 |

chunk 不是越长越好。它有一个直接的代价：**开环时间**。chunk 越长，模型对中途变化的反应越慢；遇到人突然伸手、物体滑动，机器人会按 1 秒前的计划继续走。π0 选择 50 步 / 0.5 s 一次推理，是在「减少推理次数」和「保持反应性」之间取的折中；ACT 的 100 步在 50 Hz 下是 2 秒，只适合高度结构化的任务。

2026 年的主流解法不是继续加长 chunk，而是**双系统**：GR00T N1 的 System 2 以 10 Hz 跑 VLM，System 1 以 120 Hz 跑 DiT 动作头；π0.5 则是高层子任务预测（低频）+ 底层动作 chunk（高频）。用两个时间尺度，而不是一个超长 chunk。

## 5. 2026 年的动作表示格局

把现在的开源模型按动作表示分一下：

| 表示 | 代表 | 适合 | 主要问题 |
|---|---|---|---|
| 每维 256 bin + 自回归 | OpenVLA、RT-2、π0-FAST | 复用 VLM 词表、训练简单 | 高频退化、推理慢、精度受 bin 限制 |
| 连续 + L1 回归 | OpenVLA-OFT | 快、简单、chunk 大 | 多峰时学中位数；精细任务可能糊 |
| Diffusion | Octo、RDT-1B、Diffusion Policy | 多峰表达力强 | 多步去噪、延迟高 |
| Flow matching | π0、π0.5、GR00T、SmolVLA | 10 步可出高质量 chunk | 需要 action expert；步数仍是延迟 |
| DCT + BPE | FAST、π0-FAST | 高频、长 chunk、训练省算力 | 推理自回归慢；tokenizer 需预训练 |

一个明显的趋势是：**连续动作 + flow matching + chunk 正在成为默认组合**，离散 token 退回到「需要复用 VLM 语言能力」或「需要极长时序压缩」的场景。但这不意味着离散路线失败——π0.5 的预训练阶段仍然用 FAST 离散 token，后训练才切到 flow；两种表示在同一个模型里共存，靠 attention mask 隔离。

## 小结

- 256 bin 的有效档位是 255（OpenVLA）或 256（π0.5 的 state），两者不是一回事；均匀分箱在小动作区间的相对误差可达 10%。
- 动作 token 的边际信息随控制频率升高趋近于零；50 Hz、14 维、1 秒 chunk 的 naive 表示是 700 个 token，FAST 能压到 53 个。
- FAST 省的是**训练算力**，推理反而慢 7.5 倍（750 ms vs 100 ms）。
- chunk 从 1 涨到 50 是必须的（ACT：k=1 只有 1%），但开环时间限制了上限；2026 年的解法是双系统而不是无限加长。
- 动作表示没有全局最优，只有和频率、延迟、任务精度匹配的选择。
