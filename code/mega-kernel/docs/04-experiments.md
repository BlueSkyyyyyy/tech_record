# MegaKernel 实验：105 个问题，105 个答案

> 这是一份「实验手册」。MegaKernel 的收益（省 launch、省中间量 HBM 往返、回收跨 task 流水）
> 和它的三笔代价（寄存器足迹、代码足迹、设备内协调），在这里被拆成 105 个可单独回答的问题。
> 一句话结论：**收益大多是「换掉一层数据搬运」换来的，代价大多是「把资源按最大值常驻」付出的**，
> 而两者都有明确的失效边界——本文的主要价值是把这些边界钉在具体数字上。

## 0. 先记住一个画面

把这一篇想成一次**体检**，不是一个排行榜。

体检有 105 项检查。每一项只回答一个具体问题：
「这块指标在什么条件下会变坏、坏多少、坏在哪一层」。
单独看某一项，数字没什么意义；把它和相邻几项排在一起，才能看出**哪一层是瓶颈**。

比如同样是「融合两个算子」：

- 一道检查量的是 **launch 开销**（每单元 1.75–2.2 µs）→ 它只在单元很轻时才是主项；
- 一道检查量的是 **HBM 字节**（融合后 8 B/元素 vs 未融合 `Q×8`）→ 它随算子数线性放大；
- 一道检查量的是 **寄存器足迹**（轻 task 带宽 2589 → 1132 GB/s）→ 它把前两项的收益吃掉一部分。

所以这份手册的正确读法是：**先看问题，再看数字，最后看「在什么条件下不成立」**。
每个实验的「局限」都被保留下来了，它们和结论一样重要。

> **类比的边界**：体检的指标互相独立，而这 105 项**彼此耦合**——寄存器足迹改变占用率，
> 占用率改变 HBM 带宽，带宽又改变「取 task 能不能被藏住」。
> 而且绝大多数实验是**合成负载**（自旋、`float4` 求和、读固定张量），量的是**机制上界**而非端到端。
> 把它当「某模型的加速比」会错得很离谱；把它当「某个旋钮转动一格值多少钱」才对。

读完这一篇，你应该能回答：

1. MegaKernel 的三笔代价分别由什么变量支配，各自的**失效边界**在哪？
2. 哪些优化是「真收益」（省掉一整层字节），哪些只是「把开销挪到别处」？
3. 给定一个具体瓶颈（launch / HBM / L2 / 占用率 / 放置墙），该拧哪个旋钮、别碰哪个？

## 1. 实测环境与读表口径

### 1.1 硬件与工具链（P0-3 环境探测）

| 项 | 值 |
|---|---|
| GPU | NVIDIA H100 80GB HBM3（8 卡，各实验固定占用其中一张空闲卡） |
| compute capability | 9.0（**sm90**，部分实验要求 `sm90a`） |
| SM 数 | 132 |
| shared mem / SM | 233,472 B（228 KB） |
| shared mem / block | 49,152 B（48 KB，默认；opt-in 上限 225 KB） |
| 寄存器 / SM | 65,536 |
| 每 SM 线程上限 | 2048（H100 硬限，§82 用到这条边界） |
| 驱动 | 570.211.01 |
| nvcc | release 13.2, V13.2.78 |
| CUDA runtime | 13020 |

容器 `kernel_lab` 内执行，入口脚本 `scripts/lab.sh`；各实验的原始输出落在
`code/mega-kernel/harness/*.out.txt`。

### 1.2 三项基础能力：都通了（P0-3）

| 能力 | 结果 |
|---|---|
| persistent kernel + cooperative grid sync | 可编译可运行：200 轮 grid-wide 屏障（132 block）**0.330 ms**（≈1.65 µs/次），对照 200 次 trivial launch **0.575 ms** |
| CUDA Graph capture/replay | 32 节点图：plain 200×32 次 launch **18.007 ms** → graph 200 次 replay **11.567 ms**（**1.56×**） |
| PDL | `cudaLaunchKernelEx` + programmatic 属性可启 producer/consumer，`flag` 均 =1，可做真实重叠度量 |

三项均**实测通过**，无「仅资料分析」降级项——这是后面所有实验的地基。
两个踩过的坑记在这里：legacy default stream 不能用 `cudaStreamCaptureModeGlobal` 捕获；
CUDA 13 移除了 `cudaDeviceProp::cooperativeMultiDeviceLaunch`。

### 1.3 读表口径

- **三笔损失**：损失一 = 跨 task 软件流水的空转，损失二 = launch 开销，损失三 = 中间量 HBM 往返。
- **判据 C1–C5**：单次 launch / 常驻、多算子范围、设备内协调、跨 SM 原语、worker+scheduler 动态派发。
  本文所有微基准最多满足到 **C4**，**没有一个**是完整 MPK 运行时（C5）——凡出现「仍差 C5」即指此。
- **`meas/E`**：实测吞吐 ÷ 按各模式单独跑的时间份额加权出的期望吞吐。1.0 = 无干扰，<1 = 有税。
- **`eff` / `occ`**：静态占用率 API 的读数 / ncu 实测的 achieved occupancy，两者在 cluster kernel 上会分叉（§99）。
- 所有绝对数只在**目标卡 + 本容器**内可比；跨卡比较须同卡基线（§85 量到 L2 驻留类有真实卡间差）。

## 2. 实验总表

编号即可回查附录原小节；「关键数字」只留最能定位结论的那几个。

| 编号 | 问题 | 做法（一句话） | 关键数字 | 结论 |
|---|---|---|---|---|
| P0-3 | 三项基础设施能不能在目标卡上编译、跑起来 | `probe_env.cu` 三项自检 | grid sync 200 轮 **0.330 ms**（≈1.65 µs/次）vs 200 次串行 launch 0.575 ms；32 节点 graph 18.007→11.567 ms（**1.56×**） | 三项均「实测通过」，无「仅资料分析」降级项 |
| P5-1 | 三种 launch 策略的 host / 设备侧开销各是多少 | 同一设备工作，eager / graph / persistent 扫 N、扫 K | eager 恒定 **~1.75–2.2 µs/单元**；graph ~0.8 µs/单元（~2.1×）；persistent 恒 **~2 µs**，N=4096 达 **1988×** | launch 开销只在 launch-bound 区间值得治；graph 省 host 提交，persistent 连 N 次设备 grid 启动也省 |
| P5-2 | 两算子融合省的是 launch 还是 HBM 流量 | op1/op2 逐元素，eager2/graph2/barrier/fused | M=256 Mi：fused 0.7682 vs eager2 1.5113 ms，`barrier/fused` **1.94–2.00×**；四者表观带宽均 ~2.8 TB/s；max 误差 = 0 | 损失三主导（2×，与 16→8 B/elem 吻合），损失二在本区间 ≈1.0× |
| P5-3 | PDL 串成 K 级链，收益会不会随 K 累积 | K 个 kernel 逐级 PDL 放行，扫 K=1..16 | A 组 K=16 **1.87×**（稳态 0.1091 vs 0.2042 ms）；B 组 **1.31×**；每边只重叠 `min(prologue,tail)` | 收益封顶在常数（A 组 ≈2.0×、B 组 ≈1.33×），边与边不叠加；链上只有 1 级流水 |
| P9-1 | 损失三随算子数 N 如何标度 | N 算子依赖链，四策略，扫 M / N | 带宽主导 N=32：**10.26×**；Section C 小 M：`e/persist` **1.54×**、`e/graph` 1.57×；fused 恒 8 B/elem | 融合收益 ≈N× 但 N≥8 后转入计算主导而饱和；launch 只在轻负载显形 |
| P10-1 | persistent 网格该开多大、grid.sync 多贵 | `grid` 1→1056，并行度 / 过配 / 屏障三组 | 占用上限 1056 处 speedup **212.9×**；`grid.sync` 有 **~1.1 µs 固定地板**（G=1 也 1132 ns），G=1056 2403 ns | 网格取「占用上限」而非 #SM；每 block 效率随之下降但总时间仍降；过配纯浪费 |
| P12-1 | 上游占满机器时 PDL 还能拿回多少重叠 | 一对 producer/consumer 扩到多 block | 上游接近占满 → **~0.74×ideal**（speedup 1.50×→1.33×）；低占用 0.99–1.00×；下游 grid 大小几乎无关 | PDL 是「向上游借 occupancy 余量」，天花板与 blockDim 无关 |
| P13-1 | 单 kernel 内跨 task 软件流水能拿回多少（损失一） | `cp.async` 深层 K 预取，扫 K / R / chunks | R=64：K=1→4 给 **1.18×**（2.885→2.436 µs/chunk）；纯访存 R=0 给 **2.17×** | 损失一可回收，量级 1.18×（与论文 1.2–1.3× 同档）；收益几乎全在深度 1→2 |
| P14-1 | 寄存器被固定为各 task 最大值要付多少 | 一个 kernel 内编进重 task，扫 H | 轻访存 2589→1944 GB/s（**1.33×**）→1132 GB/s（**2.29×**）；时分复用 vs 两次 launch **1.27×–1.79×**；`H≥128` 撞 254 regs 封顶 | 寄存器足迹真实可测；SMEM 可分页规避、寄存器不能，正是论文 §7 的「唯一例外」 |
| P15-1 | 去中心化 in-kernel 调度（C5）能不能真跑 | 原子 ready 队列 + `dep_count`，全程无 `grid.sync()` | 均衡负载 0.99–1.02×（C=64 L=4 反跌 **0.556×**）；异构 C=528：decen **3.863** vs eager 4.507 ms（**1.167×**）、barrier 仅 1.007× | 机制廉价且逐位正确；收益只在「task 多且负载异构」，不是「省屏障」 |
| P16-1 | 融合的 task 类型数如何经代码工作集打到 I-cache | P 个 1040 B SASS body，spread vs sticky | P=256：**2.176×**（32.1→14.7 TFLOP/s）；spread `no_instruction` 0.63%→**59.19%**；sticky 稳在 ~32.7 TFLOP/s | 代价来自「每条执行流的时间代码工作集」，非分发表；P≤8 几乎免费，有效 L1i 工作集数十 KB |
| P17-1 | 寄存器足迹与代码足迹叠加是相加还是相乘 | 同一 kernel 内同时开重寄存器与多 body | 纯计算 both **1.5747 ms** vs 相加预测 1.5731 ms（差 0.1%）、相乘预测 7.61×；混合负载 2.0149 ms（比相加低 ~14%） | 绝对时间「相加」而非相乘；但组合惩罚仍 3.795×–4.723× |
| P18-1 | `setmaxnreg` 能不能收回那 1.33–2.29× | warp-specialized + `setmaxnreg.inc/dec` | `ws(U1)` 的 `U1/naive` **0.54–0.77×**、`U1/sep` **0.92–1.24×**；不调 setmaxnreg 的 `ws(U0)` H=192/232 因 spill 爆炸到 2.69/3.96 ms（慢 7.7×）；入口 128 regs → 2 block/SM | 能基本收回（H≤192 甚至比两 kernel 更快）；代价是需 `sm90a` + 显式入口寄存器数 |
| P19-1 | PDL 与 CUDA Graph 能不能「相乘」 | 三种组合（graph / ePDL / gPDL）跑同一条 K 级链 | `gPDL/g` 逐行**等于** `e/ePDL`（A 组 1.00→1.87×、B 组 1.31×），`fail` 每格恒 0；小 span K=64：eager 6.80 µs/kernel → graph 1.18×、ePDL 1.82×、gPDL **1.97×**（相乘预测 2.15×） | Graph 完整保留 PDL 语义；两者**次乘**（挤同一段「kernel 间串行缝」），上限各自独立 |
| P20-1 | 把依赖做细（逐 tile）为什么不赢算子级屏障 | 静态切 block：producer/consumer 各占一部分 SM | `pipe/b` 恒 <1（**0.29–0.87×**）；`barrier/serial` ≈1.00–1.02×；producer 要到 GB≈132 才喂满 HBM、consumer 到 1056 仍加速 **2.41×**；三策略逐位一致 | 细粒度依赖本身不产生收益：两个阶段都要整台机器，静态分块结构性不划算；重叠载体必须是 SM 内共驻 |
| P22-1 | 扇入/扇出与 DAG 形状如何改变调度机制排名 | 分层图扫 W / FIN / SEG / L，四机制对照 | `barrier` 恒 **1.000×**；`decen` 小 task 只 0.269–0.323×，SEG 4096→32768 升到 **0.956×**；`wave` 批量 K=2–8 仅 2–3% 增益，K=16 崩到 **0.530×**、K=32 **0.270×** | 严格分层均衡图上集中式最快；动态队列是每 task 固定开销，只有 task 够长（或异构）才回本 |
| P23-1 | 跨层软件流水 + 环形缓冲预取值多少 | `ring` 用 K 页 SMEM 环形预取，对 eager/barrier/decen | `eager/barrier` 1.14×（L=8）→**1.25×**（L=256）；`ring` 比 barrier 峰值 **1.19–1.20×**（E=32 时 0.834×）；纯访存 R=0 净亏（1.036×/1.376×）；K=1→4 单调、K≈4 饱和 | 预取收益 ≈ 访存占比，随计算强度衰减；深度由访存延迟与同步 slack 决定，不是常数 |
| P24-1 | 用 ncu 直接量「融合消掉多少 HBM 流量」 | Q 个逐元素算子链，读 `dram__bytes_*.sum` | fused 恒 **518.5 MB**（≈8 B/元素）；eager/graph ≈ `Q×517 MB`，`vs_fused` = 1.99/3.98/7.96（Q=2/4/8）**精确等于 Q**；barrier 写字节多 2–4% | 时间优势完全等于省下的 DRAM 字节比（4.11× 字节 vs 4.0× 时间）；`grid.sync()` 只省 launch、一点流量不省 |
| P29-1 | 跨 SM 的中间量放 DSM 还是放 L2/HBM | cluster 内 ring 段位移 vs global scratch | 远端 SMEM 读只慢 **0–17%**（C≥4 1.163–1.177）；`dsm/hbm` **1.06→1.27×**（段 1 KB→8 KB）；`cluster.sync` 504–767 ns，比 `grid.sync` 便宜 **1.5–2.2×** | DSM 是 SMEM 级跨 SM 通道；cluster 硬上限 **16 block** 且 grid 须为 C 的倍数，132 SM 装不进一个 cluster |
| P30-1 | TMA multicast 一次读、C 个 SMEM 收值多少 | rank0 发 multicast vs 各 CTA 各发普通 TMA | delivery 随 C 线性（单 CTA 97–105 GB/s）；多 cluster 两模式都在 **6.2–6.8 TB/s** 饱和，multicast 只快 0.1–1.1%；ncu：L2 read sectors 少 **2.10×**、L2 字节少 1.84×、**DRAM 字节完全相同**（71.28 MB） | 广播省的是 L2 请求/带宽（且被 L2 合并打折），不是 DRAM；墙钟收益取决于瓶颈落在 SMEM 写还是源侧 |
| P31-1 | 2D/3D cluster 的 rank、DSM 与子集掩码 | 显式 2D/3D cluster，逐行 mask 广播 | `rank = x + y·cx + z·cx·cy`；2D DSM 环形 **552/528 GB/s**（1D 同段 560.7）；mode1 L2 sectors 少 **4.38×**，mode2 恰为 mode1 的 cy=4 倍、DRAM 4×；`cluster.sync` 448→505 ns | 机制不变、只多一层 rank 换算；multicast 省的是「同一块的重复读」，各行读不同数据时源流量照样涨 |
| P32-1 | 事件可见性能不能提前到「上游未完成」 | 六档事件（post/early/none/bstart/lce）跨 stream 放行 | `post`/`early`/`none`/`bstart` 的 `A_start→C` 都在 **~108 µs ≈ A 整段（116 µs）**；只有 `lce` 落到 **7.77 µs**；多 block 时 lce 恒 ~7.5 µs、其余随 `(G-1)*step` 线性 | 只有 LCE 能「全 block 开始即放行」；kernel 级没有「中间进度早于完成、可被依赖方看到」的原语 |
| P33-1 | SM100 `cta_group::2` 在 sm90 上怎么投影、值多少 | indep / mcast / split 三模式搬同一对 tile | 多 pair 32 KB：**mcast 快 1.21×**（`m1/m0`=0.825）、**split 慢 1.13×**（1.130）；ncu：mcast DRAM 209.76→**104.89 MB**（恰 2.00×）、L2 sectors 减半；split 源字节与 indep 完全相同 | 「复制」与「分区」是两个正交方向：2SM load 省的是协调与屏障，不省 HBM/L2 字节 |
| P34-1 | Mega Gate 的 `cluster_dim` 协调路径能否 sm90 等价复刻 | split-K + CTA pair 切专家维 + ScoreBarrier | 6 组 `SPLIT×MMA` 全部 `idx_mismatch=0`、权重误差 ~2e-7；NT=16 时 grid 16→128 拿 **3.51×**；饱和后 `fused` 比 `gate SPLIT=1` 快 **~11%**（~24 µs） | multi-CTA 逻辑任务的价值在「填机器」而非「更快」；机器填满后只剩 scratch 往返 + barrier 成本 |
| P35-1 | Graph 的 PROGRAMMATIC 边能不能把下游调度点前移到上游完成前 | 显式构图 + programmatic 端口，两节点 | `prog` 端口 = 「所有 block 都 trigger」（`sched = pro + (G-1)*stagger`）、`lce` 端口 ≈0；下游一调 `cudaGridDependencySynchronize()` 仍等上游完成（`rel ≈ A_total`）；capture **≡** 显式构图 | kernel 级能前移「调度点」，不能前移「依赖可见点」；端口太粗、要全体会合 |
| P36-1 | 一张 Graph 能不能表达数据相关 / 可变行程控制流 | IF / WHILE 节点 vs 静态展开 vs in-kernel 循环 | `cwhile` 每行程 **4.3–4.6 µs**（比 host eager ~2.2 µs 贵 ~2×，含 ~7 µs 固定项）；`kinternal` **~0.23 µs**（便宜 ~20×）；`unroll` ~0.5–0.57× eager、~1.1–1.3 µs/节点，instantiate ~1 µs/节点（N=64 → 66.5 µs） | 条件节点解决「表达能力」不解决「性能」；多轮应做成 in-kernel 计数 |
| P37-1 | 设备侧图启动能不能当 in-kernel 分发用 | 自重启图 / device graph launch | `srelaunch` **4.29 µs** ≈ host launch 的 2×、≈ host 启 1-node 图的 1.8×；单次 device 图启动 4.13 µs；`kinternal` **~40 ns/单元** | 「设备发图」不便宜：条件节点 / 自重启 / device graph launch 都落在同一个 ~4 µs 分发地板 |
| P38-1 | 整机 megakernel 与邻居的干扰 / Green Contexts 能否隔离 | 常驻 persistent + victim，扫分区与优先级 | Gp=132（1 blk/SM）→ victim **1.0×**；Gp=1056（占满）→ victim **134.5×**（5.613 ms）；gcA=64/gcB=68 → victim **0.76×**、persist 7.56 vs 单独 7.55 ms；同分区另一流 → **184.3×**；高优先级仍 **133.65×**；persist 带宽 32/64/96 SM → 1335/2277/2821 GB/s | 干扰开关是「剩余占用率槽位」不是「占几张 SM」；只有 SM 分区给硬隔离，优先级替代不了分区 |

| P176-1 | 放置悬崖的时间线长什么样 | 逐块时间线（`clock64` 打点） | `grid=1024` 多出的 **32 块（3.2% 工作量）**在 **~394 µs（0.76 span）**才开始、以 **3.2%** 占用率独跑 **~309 µs**；§100 的 −26% 由该尾波定量解释（时间比反推 0.739）；尾波**结构性、与 `R` 无关**（比值恒 1.38–1.44），`+1` 个 cluster（+0.4%）即 **+23% span**；`C=4/8` 第一波只用 **124/132** SM、`C=16` 只用 **116/132**、`C=2` 用满 132 | 必须让 `grid ≤ maxActiveClusters(C)·C`：多一个 cluster 就换来一整遍近空载的尾波 |
| P177-1 | cluster 形状（1D/2D/3D）会影响放置墙与 multicast 吗 | 同一 `C` 的所有因子分解 | API 对同一 `C` 返回相同 `maxActiveClusters`；`deliver` 与墙面位置在 1D/2D/3D 间**逐档重合（<0.3%）**，`+1` cluster 触发同一处断崖（`C=4` **+23.3%**、`C=8` **+27.6%**、`C=16` **+44.5%**）；multicast 在 2D/3D 下可用、正确、同速（**~10.9 TB/s**） | 墙只认 `C` 不认形状：维度可按语义选，避开墙的唯一旋钮仍是 `C` |
| P178-1 | 二维 tile 用多笔线性 bulk 拼，代价多少 | 连续 1 笔 vs `rows` 笔（每行 1 KB）vs 软件基线 | `expect_tx(总字节)` + 最多 **1024 笔** bulk 落同一 mbarrier **事务字节累加正确**；拆 `rows` 笔比一笔连续慢 **1.13×–1.62×**，每行再切 `K` 段后吞吐**反比于笔数**（每笔 ~**26 ns**）；小段 1 KB 的 bulk **慢于软件** `st.shared::cluster`（`rows=16`：**627 vs 740 GB/s**） | S2S bulk 的红利只在「大段」；要搬二维块应先打包成连续，而不是逐行发小 bulk |
| P179-1 | 源/目的 pitch 组合与「整段连搬 vs 逐行拆搬」 | pitch 三组合 × `rows` / `K` | 事务字节累加在任意 `spitch/dpitch` 组合下全部正确（全 grid 对拍 `maxerr=0`）；源带距/目的带距/两端带距吞吐**相差 <0.3%**——代价只由笔数 × 段大小决定；**带 padding 整段连搬严格优于逐行**：`rows=16` **1.33×–1.55×**、`rows=32` **1.72×**，且几乎达到打包天花板（`f_dd` **927** vs `p1` **975**，仅差 4.9%，还省一次打包） | 跨 SM 交付中间张量：能连搬就别拆，能保留行距就保留 |
## 3. 第 1 组：launch 开销与算子融合（§1–§7, §17）

### 3.1 这组告诉我们什么

1. **launch 开销只在「单元很轻、数量很多」时值得治**：eager 的每单元成本恒定在 **~1.75–2.2 µs**，
   与你跑多少个单元无关；一旦每个单元的计算量涨上去，三种策略就趋同。
2. **graph 与 persistent 治的是不同层**：graph 把 N 次 host 提交压成 1 次，
   persistent 连 N 次**设备侧 grid 启动**也压成 1 次。这是两个独立的信封。
3. **融合真正省的是 HBM 字节，不是 launch**：融合两个逐元素算子拿到 1.94–2.00×，
   而 HBM 读字节比 `vs_fused` ≈ Q（精确等于算子数），时间比与字节比几乎一一对应。
4. **PDL 的收益封顶在一个常数**，等于 `min(上游 tail, 下游 prologue) / span`，
   链再长也不会叠加——它只买到「一级流水」。
5. **persistent 的网格应当开到占用上限，而不是 #SM**：从 132 到 1056 还能再快 212.9×。

### 3.2 三种 launch 策略（§1 P5-1）

| N 个等量单元 | eager | graph | persistent | eager/graph | eager/persist |
|---|---|---|---|---|---|
| N=16 | 0.0294 ms | 0.0144 ms | 0.0019 ms | 2.04× | 15.35× |
| N=256 | 0.4490 ms | 0.2107 ms | 0.0020 ms | 2.13× | 227.07× |
| N=4096 | 9.1736 ms | 3.4129 ms | 0.0046 ms | 2.69× | **1987.83×** |

per-单元：eager **1.75–2.2 µs**、graph **~0.8 µs**、persistent 摊到 ~1.1 ns。
换算层数：graph 省掉的是 host 提交（1 次 `cudaGraphLaunch` 固定延迟 ~3.1 µs），
设备侧 N 次 grid 启动仍在；persistent 把这一层也省了。

### 3.3 融合的账是字节（§2 P5-2、§4 P9-1、§17 P24-1）

| 口径 | 观测 |
|---|---|
| 两算子融合（M=256 Mi） | fused 0.7682 ms vs eager2 1.5113 ms，`barrier/fused` **1.94–2.00×** |
| 表观带宽 | 四策略都 ~2.8 TB/s（说明瓶颈不在计算，在搬运） |
| 逐元素字节 | fused 恒 **8 B/元素**；eager/graph ≈ `Q × 8` |
| ncu DRAM 实测（§17） | fused 恒 **518.5 MB**；`vs_fused` = 1.99 / 3.98 / 7.96（Q=2/4/8），**精确等于 Q** |
| 时间 vs 字节 | Q=4：时间 **4.0×** vs 字节 **4.11×**（几乎完全对齐） |
| 多算子链 | 带宽主导 N=32 时 **10.26×**；N≥8 后转入计算主导而饱和 |

注意 `grid.sync()` 形态（barrier）只省 launch、**一点流量都不省**，写字节还多 2–4%。
这是「融合」与「合进单 kernel」的分水岭：判据是**中间量有没有落到 HBM**。

### 3.4 PDL 与网格大小（§3 P5-3、§6 P12-1、§5 P10-1）

| 实验 | 数字 |
|---|---|
| PDL 链 K=16（§3 A 组） | 稳态 0.1091 vs 0.2042 ms → **1.87×**，封顶 ≈2.0× |
| PDL 链 K=16（§3 B 组，tail=3×pl） | **1.31×**，封顶 ≈1.33× |
| 上游占满机器时（§6） | 从 1.50× 掉到 **1.33×**（≈**0.74×ideal**），低占用时 0.99–1.00× |
| `grid` 132→1056（§5） | speedup 到 **212.9×**；`grid.sync` 有 **~1.1 µs 固定地板**（G=1 也 1132 ns，G=1056 2403 ns） |

两条边界都很硬：PDL 是「向上游借 occupancy 余量」，借不到就没有；
`grid.sync` 的 1.1 µs 是**每次会合**的地板价，所以生产实现宁可走异步 ring barrier。

### 3.5 单 kernel 内的跨 task 流水（§7 P13-1）

`cp.async` 深预取把「损失一」回收出 **1.18×**（R=64，2.885→2.436 µs/chunk），
纯访存（R=0）能到 **2.17×**；收益几乎全在**深度 1→2** 那一步。
这与论文报的 1.2–1.3× 同档，机制相同，深度取决于「延迟/计算比」——真实 kernel 用 3–6 级，
因为要同时喂 K 与 N 两个方向。

**工程含义**：先判断瓶颈落在哪一层——host 提交、设备 grid 启动、还是 HBM 字节。
三层各有一个信封，融合只对第三层有效。

## 4. 第 2 组：资源与代码足迹（§8–§12）

### 4.1 这组告诉我们什么

1. **寄存器足迹是 megakernel 唯一绕不开的常驻代价**：SMEM 可以分页申请/释放，寄存器不行，
   一个 kernel 内所有 task 都被抬到**最重那个 task 的需求**。
2. **代价藏在占用率里，不在 spill 里**：Section A 证实 0 spill，慢是因为 warp/SM 从 32 掉到 8。
3. **代码足迹打的是 I-cache**：融合的 task 类型数一多，时间上的代码工作集超过 L1i 就开始罚，
   P≤8 时几乎免费，P=256 时 **2.176×**。
4. **两种足迹是相加，不是相乘**：both 实测 **1.5747 ms** ≈ 相加预测 1.5731 ms（差 **0.1%**）。
5. **`setmaxnreg` 能把寄存器足迹基本收回**，代价是要 `sm90a` + 显式声明入口寄存器数。

### 4.2 寄存器被钉在最大值（§8 P14-1）

| 最重 task 的 H | 轻 task 带宽 | 相对基线 | 说明 |
|---|---|---|---|
| H≤48 | 2581–2582 GB/s | 1.00× | `max(light,heavy)` 仍是轻 task 自己 |
| H=64 | 1943.7 GB/s | **1.33×** 慢 | 占用率 32→24 warp/SM |
| H≥128 | 1131.7 GB/s | **2.29×** 慢 | 撞 254 regs（sm90 上限 255）后饱和 |

时分复用形态（轻后重合一）对比两次 launch：H=32 时 **0.96×**（略快，白赚一次 launch），
H=64 **1.27×**、H=128 **1.79×**——差值几乎全是「轻阶段被寄存器拖慢」那部分。
SMEM 侧相反：32 KB/block 就把 block/SM 从 8 压到 6，但 SMEM 可以按 task 申请/释放。

### 4.3 代码足迹与双层叠加（§10 P16-1、§11 P17-1）

| P（body 数） | 吞吐 | 相对 | `no_instruction` 占比 |
|---|---|---|---|
| P=8 | ~32.7 TFLOP/s | ~1.0× | — |
| P=256（spread） | 14.7 TFLOP/s | **2.176×** 慢 | 0.63% → **59.19%** |
| P=256（sticky） | ~32.7 TFLOP/s | ~1.0× | — |

关键不是「分发表变慢」，而是**每条执行流的时间代码工作集**；sticky（同一 body 连续跑）
就完全不罚——这说明有效 L1i 工作集只有数十 KB。
两种足迹叠加时：纯计算 both **1.5747 ms**，相加预测 1.5731 ms（差 **0.1%**），
相乘预测 7.61× 远高于实测；混合负载 2.0149 ms（比相加还低 ~14%）。
但组合惩罚仍是 **3.795×–4.723×**——「不相乘」不等于「不贵」。

### 4.4 setmaxnreg 的回收（§12 P18-1）

| 形态 | 相对 |
|---|---|
| `ws(U1)` vs naive（不调 setmaxnreg） | **0.54–0.77×**（即快 1.3–1.9×） |
| `ws(U1)` vs 两次 launch | **0.92–1.24×**（H≤192 时甚至更快） |
| `ws(U0)` H=192 / H=232 | 2.69 / 3.96 ms（慢 **7.7×**，因为 spill） |

入口 `__launch_bounds__(256,2)` 把入口钉在 128 regs → 2 block/SM，
warp 角色再在运行时重分配。但 H=232 已逼近 2× 入口预算，仍有残余 spill。

**工程含义**：把「寄存器预算」当成每 task 的**接口契约**来设计，
而不是让最重的 task 决定整张卡——这正是 §81 那条「不要为保险多要寄存器」的另一面。

## 5. 第 3 组：设备内调度与队列协议（§9, §15, §16, §31–§38）

### 5.1 这组告诉我们什么

1. **去中心化调度（C5）能跑、而且逐位正确**，但它不是「省掉屏障」的魔法：
   均衡负载下 **0.99–1.02×**，只有 task 多且异构时才赚（**1.167×**）。
2. **死锁边界不是「池容量」，是一个「阻塞数」**：`B(π)+1` 才是真边界，
   而且层号 ≠ 拓扑序时 `level` 口径会失效。
3. **事件驱动「就地入队」把阻塞数从 `B(π)` 直接压到 0**——从机制上消掉死锁，而不是靠加容量。
4. **发布内存序不能省**：sm90 允许 store→load 重排（litmus 100% 观测到），
   naive 发布在环上**必错**；release/acquire 的代价是 **+0.36 µs/槽**的固定项。
5. **多生产者必须「连续放行」**（完成门控），消费侧的摊薄要靠**多线程并行读**而不是批量。

### 5.2 调度的收益与 DAG 形状（§9 P15-1、§15 P22-1、§16 P23-1）

| 实验 | 数字 |
|---|---|
| 去中心化 vs eager（均衡） | 0.99–1.02×；C=64 L=4 时反而 **0.556×** |
| 去中心化 vs eager（异构 C=528） | **3.863 vs 4.507 ms（1.167×）**，而 barrier 只有 1.007× |
| 分层图上四机制（§15） | barrier 恒 **1.000×**；decen 小 task **0.269–0.323×**，SEG 4096→32768 升到 **0.956×** |
| wave 批量化（§15） | K=2–8 仅 2–3% 增益，K=16 崩到 **0.530×**、K=32 **0.270×** |
| 跨层预取（§16） | eager/barrier 1.14×（L=8）→ **1.25×**（L=256）；ring 比 barrier 峰值 **1.19–1.20×** |
| 预取净亏（§16，纯访存 R=0） | **1.036× / 1.376×** 的净损失 |

读法：动态队列的成本是「每 task 一笔固定开销」，所以它只在 task 够长、够不均衡时才回本；
在严格分层均衡图上，集中式 barrier 永远最快。

### 5.3 有界 ready 池：死锁边界（§31–§35）

| 实验 | 结论与数字 |
|---|---|
| §31 P42-1 | 坏准入顺序必死锁；最小 warmup 宽度 = 全部 producer；容量 ≥ 活跃 task 数才满吞吐 |
| §32 P43-1 | 边界 = **阻塞数 B**，且是 **(CAP,G) 联合约束**：`L=6/8、G=64` 时**任何 CAP 都死锁**（「边界=B+1」被推翻） |
| §33 P44-1 | 闭式 `(L-1)*W0` 失效，真边界 **`B(π)+1`**；层号乱序时 `level` 口径失效 |
| §35 P46-1 | 「队列无界」不成立：**`CAP_safe + G ≈ W_max + 1`**；超容量不再提速，边界附近「单次可完成、多次可能死锁」 |
| §34 P45-1 | `scan`/`topo`/`event` 三机制 **B ≡ 0**（任意 DAG 都不死锁），且四机制数值逐位一致 |

这两次「预测被实测推翻」值得单独记一笔：先猜「容量 = 阻塞数 + 1」，实测发现要**(CAP,G) 联合**；
再猜「层宽闭式」，实测发现要**真拓扑线性化**。

### 5.4 发布内存序与消费者的摊薄（§36–§38）

| 实验 | 数字 |
|---|---|
| §36 P47-1 litmus | sm90 **保序 store→store、允许 store→load**（SB 100% 重排） |
| §36 五档发布序 | `pubslp` **必错**；`pub`/`half`/`wro`/`rel` 实测 0 错（但前者是侥幸） |
| §36 代价 | release/acquire **≈ +0.36 µs/槽**，几乎恒定 |
| §37 P48-1 | 两种「完成门控」协议任意生产者数 / 容量 **0 错**；`stall0` 正对照让「侥幸写法」露馅；放行 **≈ +0.38 µs/项** |
| §38 P49-1 | 单线程批量出队只收回 **1.2–1.5×**；warp 消费者在 128 B 下快 **21×**（每项 ~300 ns），瓶颈随即翻到生产者 |

**工程含义**：调度机制本身很便宜（几十 ns 到几百 ns 量级），
真正贵的是**同步频率**和**内存序栅栏**——所以设计目标是「把同步次数降到最低」，
而不是「把单次同步做快」（这条在 §10 组被反复验证）。

## 6. 第 4 组：细粒度重叠与 PDL/Graph 的边界（§13, §14, §21, §24–§26）

### 6.1 这组告诉我们什么

1. **把依赖做细并不产生收益**：静态切 block 让 producer/consumer 分占 SM，
   实测 `pipe/b` 恒 <1（**0.29–0.87×**），比算子级屏障还差。
2. **PDL 与 CUDA Graph 是「次乘」不是「相乘」**：它们抢同一段「kernel 间串行缝」。
3. **kernel 级 API 只能前移「调度点」，不能前移「依赖可见点」**：
   下游一旦 `gridDependencySync()`，仍旧等上游完成。
4. **凡是「设备侧重新分发 kernel/图」的机制，单价都在 ~4 µs**——
   条件节点、自重启图、device graph launch 都撞在同一个地板上。
5. **数量级更低的路只有一条：不跨边界**（留在同一个常驻 kernel 内，~40 ns/单元）。

### 6.2 细粒度重叠为什么输（§14 P20-1）

| 策略 | 相对串行 |
|---|---|
| `barrier`（算子级屏障） | 1.00–1.02× |
| `pipe`（静态切 block） | **0.29–0.87×** |

原因是结构性的：producer 要 **GB≈132 个 block** 才能喂满 HBM，
consumer 到 **1056 个 block** 仍能加速 **2.41×**——两个阶段都想吃整台机器，
静态分块必然两头不讨好。这也解释了为什么重叠的载体必须是**同 SM 内共驻**。

### 6.3 PDL × Graph（§13 P19-1）

| K=64（小 span） | 每 kernel | 相对 eager |
|---|---|---|
| eager | 6.80 µs | 1.00× |
| graph | 5.75 µs | 1.18×（消损失二） |
| ePDL | 3.74 µs | 1.82×（消损失一特例） |
| gPDL | 3.45 µs | **1.97×**（叠加） |
| 「相乘」预测 | — | 2.15× |

实测只有相乘预测的 **~0.92×**：graph 单跑每 kernel 省 ~1.05 µs，
但在 PDL 之下这段缝已被「下游 grid 提前启动」吃掉，边际收益降到 ~0.28 µs。
正确性上反而干净：`gPDL/g` 在所有 K 上**逐行等于** `e/ePDL`，四策略 `fail` 恒 0
——**CUDA Graph 完整保留 PDL 语义**。

### 6.4 Graph 的能力边界（§21 P32-1、§24 P35-1、§25 P36-1、§26 P37-1）

| 原语 | 放行点 | 数字 |
|---|---|---|
| `post`/`early`/`none`/`bstart` 事件 | 上游完成后 | `A_start→C` 都在 **~108 µs ≈ A 整段（116 µs）** |
| `LaunchCompletionEvent` | 所有 block **开始** | **7.77 µs**（多 block 时恒 ~7.5 µs） |
| Graph `programmatic` 端口 | 所有 block 都 trigger | `sched = pro + (G-1)*stagger`；`lce` 端口 `sched≈0` |
| Graph 条件节点 WHILE | 每行程重分发 | **4.3–4.6 µs**（含 ~7 µs 固定项，比 host eager ~2.2 µs 贵 ~2×） |
| 设备侧图启动 | 自重启一次 | **4.29 µs**（host launch 的 2×、host 启 1-node 图的 1.8×） |
| in-kernel 循环 | 不跨边界 | **~0.23 µs/行程**（比 `cwhile` 便宜 ~20×）、**~40 ns/单元** |

静态展开（`unroll`）仍是 launch 摊薄的赢家（~0.5–0.57× eager、~1.1–1.3 µs/节点），
但每换一个形状要重新 instantiate（~1 µs/节点，N=64 → 66.5 µs）。

**工程含义**：CUDA Graph 这条降级路线能走到「调度级」，走不到「依赖级」；
真正的数量级提升只能来自「不重新发 kernel」——这正是把多轮做成 in-kernel 计数的理由。

## 7. 第 5 组：多租户与 L2 常驻（§27–§30）

### 7.1 这组告诉我们什么

1. **干扰的开关是「剩余占用率槽位」，不是「占了几张 SM」**：
   铺满 132 个 SM 但每 SM 只占 1/8 槽位时，邻居 **1.0× 无感**；占满槽位则邻居慢 **134.5×**。
2. **只有 SM 分区给硬隔离，且隔离是双向的**；流优先级不能替代分区（高优先级照样被饿死）。
3. **分区的代价是线性的**：给邻居留 SM = 按比例削减自己的可达带宽。
4. **MPS 的线程容量是硬上限，且最糟点在「略低于 100」**。
5. **L2 常驻是零和交易**：carveout 从普通 L2 里划，划多了普通流受害，
   `S≥32 MB` 时 persisting 反而比不设慢 1.47–2.20×。

### 7.2 共存干扰与分区（§27 P38-1、§28 P39-1）

| 形态 | victim 延迟 |
|---|---|
| 单独跑（基线） | 0.042 ms |
| persistent `Gp=132`（1 blk/SM，可共驻） | 0.040 ms（**1.0×**） |
| persistent `Gp=1056`（占满整机） | 5.613 ms（**134.5×**） |
| Green Contexts：A=64 SM 占满 / B=68 SM 隔离 | 0.031 ms（**0.76×**），且 persist 7.56 vs 单独 7.55 ms |
| 同分区另一条流（对照） | 7.593 ms（**184.30×**） |
| 高优先级 victim vs 低优先级 persist | 5.615 ms（**133.65×**） |
| persist 分到 32 / 64 / 96 SM | **1335.3 / 2276.7 / 2821.3 GB/s** |

跨进程则是另一套语义（§28）：无 MPS 时 victim 1.792 ms ≈ 基线 1.781 ms（**1.006×**），
persist 只慢 1.4%——设备在 kernel 间时分/抢占，**同进程并发反而比跨进程无 MPS 更糟**。
MPS 默认（各 100%）是真并发，victim **1.55×**；线程容量 cap 下：
P=90 → **9.90×**、75 → 3.98×、60 → 2.80×，`P≥50` 服从 **≈1/(1−P)**。

### 7.3 中间量能不能住 L2（§29 P40-1、§30 P41-1）

| 条件 | 结果 |
|---|---|
| `S≤16 MB` 且写读紧邻 | K2 命中 **90–96%** |
| 中间插 512 MB polluter | DRAM 读恰 **= S**、命中掉到 52% |
| 加 persisting 窗口 | 相对 pollute 降 DRAM 读 **23–30%**、命中 62% |
| `S≥32 MB` | 反噬 **1.47× / 2.17× / 2.20×**（S 越大越糟），`S≥48 MB` 完全等于不设 |
| 调参（§30） | 只划 carveout 不保护：4 MB 0.996 → 16 MB **1.204** → 31 MB **1.921** |
| 最优 | **carveout=16、hitRatio=1.0 → 0.860×** |
| carveout 偏小（8 < 需求 16） | `f=1.0` → **1.026×**（thrash）；`f=0.5` → **0.879×** |
| 双窗口共存 | carve=16 全保护 **0.814×**；carve=31 → **1.343×** |

**工程含义**：多租户下先问「我要的是隔离还是吞吐」——要隔离只能用 SM 分区并接受线性掉带宽；
要吞吐就让邻居共享 SM。而 L2 常驻只在「中间量 ≤16 MB 且写读之间没有大流穿过」时成立。

## 8. 第 6 组：控制面——取 task、环协议、动态生产者（§39–§58）

### 8.1 这组告诉我们什么

1. **取 task 的载体要选「成本与描述符大小解耦」的那个**：`cp.async` 的单价与描述符大小无关，
   这是它真正的杀手锏，而不是那点带宽。
2. **环深 `D` 不是性能旋钮**：`D=2` 就到顶；接入动态生产者后，`D>1` 甚至**语义上不可得**。
3. **控制面取数可以被打满的数据面完全藏住**（趋 `max` 而非相加），前提是环深 ≥3 且批量够大。
4. **动态生产者「现场生成」在量级上不成立**：单 SM 写 352 B×NDESC 打不过整机读，
   最好情形也只到读端峰值的 ~1/4。
5. **握手税的真凶是 `release` 的 GPU 级 MEMBAR + 每批会合**，不是 acquire、不是 proxy fence；
   而到了端到端，**环容量与背压频率又盖过这一切一个量级**。

### 8.2 取 task 的载体、带宽与环深（§39 P50-1、§40 P51-1、§41 P52-1、§42 P53-1）

| 实验 | 数字 |
|---|---|
| `cp.async` 的成本 | **与描述符大小无关**；单 block 绝对带宽 2–6 GB/s（只看同节相对差） |
| 多 worker 标度（§40） | per-worker 恒 **~3 GB/s**，aggregate 随 G **线性**、到 G=2×SM 仍未饱和；真实 352 B 描述符下 **TMA bulk 双缓冲是唯一赢家** |
| 环深（§41） | **D 从 1→2 就拿到全部预取收益，D≥2 完全平坦**；固定 SMEM 预算下「更大 K、D=2」单调胜出；逼近 opt-in 上限 225 KB 仍正确 |
| 载体对比（§42） | `cp.async` 中小 K 反超 bulk、K=128 处被反超；两载体 D≥2 平坦，`cp.async` 稳态高 **~1.17×**；它省下的寄存器对下游 task **没有收益** |

### 8.3 取数能被执行藏住吗（§43–§46）

| 实验 | 数字 |
|---|---|
| 计算强度 R（§43） | 预取收益随 R 单调衰减、绝对收益恒定；**`D=3 ≈ max(fetch, exec)`**；`D=1` 已落在 `exec + ~0.02 ms`（0.74–0.99×） |
| 吃 HBM 的执行（§44） | 仍趋 **max**；`D3−exec` 跨 EDW 恒定 **0.01–0.02 ms**；数据面只到 **~1.2–1.4 TB/s** |
| 数据面饱和（§45） | T=1024 时 `D=2` 仍趋 max；数据面要「多线程」、控制面要「少线程」（相反最优）；占用率被 SMEM 环 + 寄存器锁在 **1 block/SM**（K=128,D=2 → 88 KB/block） |
| 多 block/SM（§46） | 数据面饱和的旋钮是「**每 SM 总线程数**」；控制面对 K 敏感、对占用率不敏感 |

### 8.4 动态生产者：为什么「现场生成」不成立（§47–§51）

| 实验 | 数字 |
|---|---|
| 三来源分解（§47） | 调度握手 **~8.5×**、现场生成 **~227×**；有界环 CAP 阈值落在 `(G·K, 2·G·K]` |
| 多块并行（§48） | `gen` 的 ~1/P 只到 **P≈8 饱和**；P=128 的退点是消费者瓶颈 |
| 向量化（§49） | 砍 **2–3.5×**、饱和点 P≈8 → **P>64**，仍追不平 static；瓶颈是 **store 发射**而非 DRAM 写带宽 |
| TMA bulk store（§50） | 最好情形 **~828 GB/s**（≈寄存器 v4/coop），**正确握手只有 472 GB/s**（比标量快 2.3×、比 v4 慢 1.7×）；同期读端 **809–3000 GB/s** |
| 窗口发布（§51） | §50 的预测**被证伪**：纯写 454→463 GB/s（**+2%**），深窗也只 +1.6% |

一句话：**描述符通路读端可达 HBM 峰值、写端任何载体都到不了**，
所以 MPK 选「编译期预计算 + 批量读」，而不是「设备现场生成」。

### 8.5 握手税的三维归因（§52 P63-1、§53 P64-1、§54 P65-1）

| 项 | 代价 |
|---|---|
| `st.release.gpu` | ~**500 cycles**（两条 MEMBAR） |
| `__syncthreads()` | ~**860 cycles** |
| 完成等待 | ~**430 cycles** |
| 合成效果 | store-only 630 GB/s → **437 GB/s**；摊薄发布 `S=32` → **569（+30%）** |
| 载体无关性（§53） | 分解同形、代价绝对：占比 29.9%（tma）→ **36.8%（regD）**；握手税 **~2.0–2.4k cycles/batch**；地板 609.9 / 588.7 / **721.6**，完全握手后 **455.8 / 427.5 / 390.4** |
| 端到端（§54） | **环容量绑定**时「背压×容量」主导（**~20×**）、与 `P` 几乎无关；不绑定时 §53 归因复现但衰减到 **~1.1–1.2×**（原 1.44×） |

§51 曾以为「只拆一个就够快」，§52 证明那是**单整数编码重叠**造成的假象；
真实是「L 型加性」：三笔代价各自独立、线性叠加。

### 8.6 预取深度与环协议（§55–§58）

| 实验 | 数字 |
|---|---|
| `D` 的纯性能上限（§55） | D=1→2 仅 **+7~19%**、D≥2 无增益；端到端只 **+2–3%** |
| `D>1` 的可用性（§55） | 紧环 `CAPp=16` 时跨步 `D>1` **死锁**；连续分配在 producer 被拆时**静默错**；唯一正确形态 `strided + D=1`（4.8 GB/s） |
| 每槽回收（§56） | 解锁正确性（`perslot+contig` D=1..8 全 OK），但**不解锁** `strided+D>1`；闭式阈值 `CAPp≥D` / `CAPp≥bp`；协议开销 **1.3–1.4%**；contig 正确档只 **3–3.5 GB/s**（strided ~17） |
| 每 worker 独立环（§57） | `prefix + D>1` 变正确，阈值 **`CAPp* = D`**；`pair` 相对 shared-strided 宽松环 **1.45×**；D 自身增量仅 +6% |
| 少 producer × 多环（§58） | 正确性与 `PS` 无关；**`PS*` 随 task 重量下降**：`CW=0` 需 ≈G、`2^16→8`、`2^18→≈4`（`PS:G≈1:25–1:32`，正对 MPK 的 4:128） |

**工程含义**：控制面的设计顺序是——先把环开够大、批量取够多，再谈内存序与载体；
反过来优化单条 `release` 是抓错了量级。

## 9. 第 7 组：数据面、占用率与共驻税（§59–§85）

### 9.1 这组告诉我们什么

1. **数据面的天花板是「每 SM 在飞 load 数」**：靠 ILP（`U`）与占用率（`O·T`）两条路都能爬到，
   封顶在 HBM **96%**；寄存器预算只通过占用率间接起作用。
2. **`O·T` 是饱和区的唯一合量**（组内极差 ≤1.06×），但对 L2/延迟受限的模式要「多而小」的 block。
3. **两类异构共驻税**：发射受限 × 访存受限恒低 ~13%（`(T,O)` 不可补），
   稀疏低掺杂最隐蔽（`meas/E` 掉到 0.855）。
4. **SM 角色绑定不能收回税**：`bind ≈ interleave` 逐行不变，ncu 计数逐项相同；
   分配器还必须用 in-situ 曲线 + 多起点。
5. **税的真实支配量是「每 SM 在飞 warp × ILP」**：`Wsm` 从 256 涨到 2048，税从 0.772 收到 0.995；
   块粒度 `T` 只是 ~4% 的次级量，且受益方是发射受限那一半。

### 9.2 真实 HBM 数据面：配比与饱和（§59–§62）

| 实验 | 数字 |
|---|---|
| 访存重量 MD（§59） | `MD=0 → PS*≥G`、`512 KB → 16`、`2 MB → ≈4`（1:25）；叠加后 `PS*=8`；数据面 650→952 GB/s 不降 |
| ILP 推到饱和（§60） | 926 → **2840 GB/s（峰值 85%）**；饱和点上加 producer **不拖慢**（2792 vs 2763–2837）；`PS*≈8` |
| 到真 HBM 峰值（§61） | **3219 GB/s = 峰值 96%**（峰值按 3.35 TB/s）；TMA bulk ~3075；**真峰值下描述符写拖慢 3–7%** |
| 端到端夹层（§62） | 同二进制数据面 **3156 GB/s（94%）**；端到端最优**不是满占用率**（85% 那条 2831）；`G=528~1040` 反降到 **53–62%**；分解后 fold ≈ 0、环 + producer 主导 |

### 9.3 控制面扇出住在 worker prologue（§63–§66）

| 实验 | 数字 |
|---|---|
| producer 服务模型（§63） | 每批成本**恒定**，`wpp=1→64` 吞吐**持平**——§62 的「producer 环扇出」归因被隔离证伪 |
| 四档阶梯（§64） | `G` 依赖住在 worker 每 block 一笔固定 prologue：plain **~0.35 µs/block**、TMA **~0.69 µs/block** |
| `cp.async` 进阶梯（§65） | TMA 的 +0.3 µs/block 是 **TMA 专属**：`cp.async` ≈ plain（−0.04…+0.005 µs/block）；排序 **cp.async ≥ plain > TMA** |
| `cp.async` 深环（§66） | 深环**无收益**、随 `DCA` 单调变差；单缓冲最优（±1%）；`DCA=4→5 blk/SM`、`DCA=8→2 blk/SM` |

### 9.4 寄存器预算、占用率与 `O·T`（§67–§70、§81）

| 实验 | 数字 |
|---|---|
| 跨二进制偏移（§67） | 8 B 溢出 = `__launch_bounds__(256,8)` 的 **32-reg 上限**；plain 需 `MINB=4`、TMA 需 6、`cp.async` 不需要；耐压序 **`cp.async`(≤32) > TMA(~40) > plain(~52)** |

`T` 只值 ~4%，且它的收益要记在发射受限 task 的 LSU 背压上。

## 10. 第 8 组：片上互联、cluster 与放置墙（§18–§20, §22–§23, §86–§104）

### 10.1 这组告诉我们什么

1. **DSM 是「SMEM 级」的跨 SM 通道**：远端读只比本地贵 0–17%，比走 L2 往返快 6–27%。
2. **广播省的是 L2 请求，不是 DRAM 字节**：multicast 的墙钟收益 ≤5%，
   而且必须 `g≥4` 才为净正；真正的价值是把 L2 余量让给别的 task。
3. **跨 SM 交换的正确形态是「远端写 + 本地读」**，不是远端读——后者在重负载下稳定地
   `unspecified launch failure`。
4. **同步原语有一条经济学**：每 round 一次 `cluster.sync` 是当前最便宜的可用点；
   把粒度细化到每槽（mbarrier / TMA 记账）都更慢（1.10–1.92×）。
5. **cluster 有一个「放置墙」**：`grid` 超过 `maxActiveClusters·C` 就多出一整遍近空载的尾波
   （+0.4% 工作量 → **+23% span**），而墙只认 `C`、不认形状。

### 10.2 DSM 与 multicast（§18 P29-1、§19 P30-1、§20 P31-1）

| 实验 | 数字 |
|---|---|
| 远端 SMEM 读 | `C=2` 与本地一致（0.99×），`C≥4` 只慢 **~17%**（1.163–1.177） |
| ring 段位移 | `dsm/hbm` **1.06 → 1.27×**（段 1 KB→8 KB）；`Sd` 1330 GB/s 已超 L2 往返的 1049 GB/s |
| 群屏障 | `cluster.sync` **504–767 ns**，比 `grid.sync` 便宜 **1.5–2.2×** |
| 容量边界 | cluster 硬上限 **16 block**，grid 必须是 C 的整数倍 → 132 SM 装不进一个 cluster |
| multicast（§19） | delivery 随 C 线性（单 CTA 97–105 GB/s）；多 cluster 两模式都在 **6.2–6.8 TB/s 饱和**，multicast 只快 0.1–1.1% |
| ncu（§19） | L2 read sectors 少 **2.10×**、L2 字节少 1.84×、**DRAM 字节完全相同**（71.28 MB） |
| 2D/3D（§20） | `rank = x + y·cx + z·cx·cy`；2D DSM **552/528 GB/s**（1D 同段 560.7）；mode1 L2 sectors 少 **4.38×**，mode2 恰为 cy=4 倍、DRAM 4× |

### 10.3 SM100 2SM 的 sm90 投影（§22 P33-1、§23 P34-1）

| 实验 | 数字 |
|---|---|
| 三模式搬同一对 tile | 32 KB 多 pair：**mcast 快 1.21×**（`m1/m0`=0.825）、**split 慢 1.13×** |
| ncu | mcast DRAM 209.76→**104.89 MB**（恰 2.00×）、L2 sectors 减半；split 源字节与 indep 相同 |
| Mega Gate 复刻（§23） | 6 组 `SPLIT×MMA` 全 `idx_mismatch=0`、权重误差 ~2e-7；NT=16 时 grid 16→128 拿 **3.51×**；饱和后 `fused` 比 `gate SPLIT=1` 快 **~11%（~24 µs）** |

「复制」与「分区」是两个正交方向：2SM load 省的是协调与屏障，不省 HBM/L2 字节；
multi-CTA 逻辑任务的价值在**填机器**，机器一满就只剩 scratch 往返 + barrier 成本。

### 10.4 cluster 交换的同步经济学（§86–§92）

| 载体 | 形态 | 数字 |
|---|---|---|
| `pull`（远端读） | 每线程多笔 `ld.shared::cluster` | `C≥2` 中等规模**稳定 `unspecified launch failure`**；失败边界对 `U` **非单调**（U=1/16 失败、U=8 通过），`#pragma unroll 1` 救不活 |
| `push`（远端写 + 本地读） | 每 round 两次 `cluster.sync` | **100% 稳定**（`U=1..16`、`grid≤528`、20 次重复）；吞吐 **216 → 2157 GB/s**（U=1→16） |
| `ring1`（单次 sync） | 环形槽 | 低-`U` 吞吐抬 **1.1–1.6×**（`C=8,U=1` 1.62×），省下每 lap 恰一次 `cluster.sync`（`C=2` ~0.4 µs），稳到 `grid=1056` |
| `ring`（零 sync） | 每槽 release/done | **不可用**（间歇 `unspecified launch failure`、边界非单调） |
| `mbar`（cluster mbarrier） | 每槽 release/done | 可行、稳定、逐位正确，但比 `ring1` 慢 **1.32–1.92×** |
| `mbarb`（每 block 一次 arrive） | `count=1` + `__syncthreads` | 最慢：`U=8` 时 **828** vs `mbar` **1094** vs `ring1` **1622**，倒亏 **25–50%** |
| `mbarw`（每 warp 一次 arrive） | 保留 fence | `mbarw0` = `mbar` 的 **0.861×**，`mbarw` = **0.596×**（比 `mbarb` 还慢 0.78×） |
| `mtex`（`expect_tx` 做 ready） | TMA 事务计数 | 可行、`maxerr 0`、消费者无需预 arm；比 `mbar` 快 **6–14%**，仍慢于 `ring1` **1.15–1.80×** |
| `mtex2`（双向 TMA） | ready + ack 都交给 TMA | 比 `mtex` 快 **1–17%**、比 `mbar` 快 **7–30%**，仍慢于 `ring1` **1.10–1.56×** |

另有三条诊断量：显式 cluster fence 是**每 round ~1 µs 的固定项**，与 fence 条数（`NW×2`）无关；
`mbarrier` 的 suspend-hint 必须与等待粒度匹配（不匹配时出现 ~**15×** 塌陷，数值仍正确）；
`__maxnreg__` 对 cluster 交换几乎是 no-op（占用率 8↔5，DSM lap 只差 ~3%）。

### 10.5 放置墙与 S2S bulk（§93–§104）

| 实验 | 数字 |
|---|---|
| delivery × 占用率（§93） | 每 SM 块数 1→4–6：**~2.7 → ~7.0 TB/s（2.6×）**；multicast 墙钟收益 ≤5%、`eff≥4` 才为正（低占用率反而慢 3–4%）；源侧 L2 sectors 1.02→**1.29×** |
| 子集扇出（§94） | 源侧 sector **精确 = `delivered/(32·g)`**；plain 已有 ~3.7× 合并 → plain:整群广播 **≈2.1×**（不是 8×）；`g=1` 慢 ~2×、`g=2` 慢 ~18%，**`g≥4` 追平、`g=8` 略胜 ~2%** |
| chunk 维度（§94） | 2 KB **2.07**、8 KB **7.10**、16 KB **11.22 TB/s**——§93 的「~7 TB/s 墙」是 8 KB 的产物 |
| 掩码形状（§95） | 连续/离散位图墙钟 **±2%**、L2 sector **逐位相同**；发起者身份自由（**±1.5%**） |
| 重叠掩码（§96） | 同 payload（`idem`）全 0 撕裂；不同 payload **8.9%–16.2% 撕裂**；成本只认笔数（4× 发送只慢 **×1.18**） |
| 占用率交叉验证（§99） | `occ` 与 achieved 逐档吻合（6→5.2、3→2.9、2→2.0、1→1.0）；`C=4, grid=1056` 只有 **6.7–6.95 块/SM（42–43%）**；`pad=0`（6.95 块）**6654 GB/s 低于** `pad=16`（5.20 块）**7171** |
| cluster 感知 API（§100） | `C=2/4/8/16 → 8.00/7.52/7.52/7.03` 块/SM；`C=2` 无墙；`C=4` 墙在 `grid=992`、峰值 **9.62 TB/s**，`grid=1024` 崩到 **7111（−26%）** |
| 尾波时间线（§101） | `grid=1024` 多出的 **32 块（3.2%）**在 ~**394 µs**（0.76 span）才开始、以 3.2% 占用率独跑 ~**309 µs**；`+1` cluster（+0.4%）→ **+23% span**；`C=4/8` 第一波只用 **124/132** SM、`C=16` 只用 116/132 |
| 形状（§102） | 1D/2D/3D 逐档重合 **<0.3%**，断崖位置相同（`C=4` **+23.3%**、`C=8` **+27.6%**、`C=16` **+44.5%**）；multicast 在 2D/3D 下 **~10.9 TB/s** |
| 非连续搬运（§103） | `expect_tx` + 最多 **1024 笔** bulk 事务字节累加正确；拆 `rows` 笔比一笔连续慢 **1.13–1.62×**；每笔 ~**26 ns**；1 KB 小段的 bulk **慢于软件**（627 vs **740 GB/s**） |
| pitch 组合（§104） | 源/目的/两端带距吞吐**相差 <0.3%**；带 padding 整段连搬严格更优：`rows=16` **1.33–1.55×**、`rows=32` **1.72×**，接近打包天花板（927 vs 975，差 4.9%） |

**工程含义**：cluster 用法只有三条硬规则——`C` 尽量小、`grid ≤ maxActiveClusters(C)·C`、
同步点每 round 只留一个；剩下的（形状、掩码、发起者）在硬件代价上都等价，可按语义自由选。
## 11. 三句话小结

- **收益来自「换掉一层搬运」，代价来自「按最大值常驻」**：融合省的是中间量的 HBM 字节
  （`vs_fused` 精确等于算子数）、DSM 省的是 L2 往返（1.06–1.27×）、persistent 省的是
  N 次设备侧 grid 启动（1988×）；而寄存器足迹（1.33–2.29×）、代码足迹（2.176×）、
  放置尾波（+23% span）都是「把资源按最大需求常驻」的账单。
- **每个旋钮都有一个「够用即止」的点，过了就是负收益**：环深 `D=2`、批量 `K≈W/G`、
  L2 carveout 16 MB、`U≈8`、cluster `C=2`、`grid ≤ maxActiveClusters·C`——
  这些都不是调参技巧，而是机制本身的上界。
- **同步频率比同步实现更重要**：从 `grid.sync` 的 1.1 µs 地板，到每 round 一次
  `cluster.sync`，再到每槽 mbarrier / TMA 记账（1.10–1.92× 更慢），
  每一次「把粒度做细」都输给了「把次数降下来」。
