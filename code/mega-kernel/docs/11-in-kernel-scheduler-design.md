## 0. 一句话：megakernel 的瓶颈从「算」转向「管」

kernel-per-operator 的调度权在 host，megakernel 把它搬进 device——于是**同一个常驻 kernel 内部
如何把 task 分给 SM** 成了新的关键路径（判据 C4/C5，`docs/00` §3.2）。MPK 的答案是一个
**固定角色 + 事件驱动**的两层结构（`docs/01` §4 精读、快照 §5 行 1147–1368）：

- **角色在 launch 时定死**：少数 SM 做 scheduler（每 SM 2 warp、共 16 warp、占 4 个 SM），
  其余 SM 一 SM 一个 worker，各持**独立 task 队列**（MPK 每 token 293 launch → in-kernel 调度只剩
  **0.28%**，§6.6 行 1618–1628；MPK 在 H100 上是 **4 scheduler SM : 128 worker SM = 1:32**，
  §5 行 1157–1164、§6.2 行 1460）。
- **事件驱动**：task 完成→通知它触发的 event→event 全部前置到齐即激活→派发下游 task（§5.1 行 1175–1231）。
  「task 就绪」不是一个被扫描发现的谓词，而是「最后一个前置完成」这个**事件**（`docs/04` §34.1）。

本专题从 P42 起，把这套结构拆成六个独立旋钮逐一实测。下面 §1 给参考架构，§2–§7 分层给结论，
§8 给成本模型速查表，§9 给决策表，§10 对它回到 MPK/DeepGEMM 印证，§11 记局限。

## 1. 参考架构：一个 in-kernel scheduler 的六个部件

把 §31–§58 的实验骨架抽象出来，任何 mpk 式调度器都由这六件组成；**每一件都有对应实测**：

| # | 部件 | 你要决定的 | 对应实验 |
|---|---|---|---|
| 1 | **调度拓扑** | 中心化（一个 scheduler block / 逐层 `grid.sync`）还是去中心化（事件驱动就地入队） | §31–§34、§15（P22-1） |
| 2 | **ready 结构** | 有界池 / 环形缓冲 / per-worker 环；容量多大、准入顺序 | §31–§35、§55–§58 |
| 3 | **入队协议** | 事件计数器 / 扫描门控 / 预计算拓扑序；完成者直接 push | §34 |
| 4 | **队列内存序** | relaxed / release-acquire；多生产者是否要「连续放行」 | §36–§37 |
| 5 | **worker 取 task** | 载体（标量/`uint4`/`cp.async`/TMA bulk）× 批量 `K` × 环深 `D` × 线程数 | §39–§46 |
| 6 | **描述符来源** | 编译期预计算 + 调度（推 id）还是设备现场生成（造 payload） | §47–§54 |

## 2. 调度拓扑：中心化 vs 去中心化

**去中心化的意义不是「省屏障」**。`docs/04` §5（P10-1）先量出 cooperative `grid.sync()` 在 132 block 上
**本就很便宜**（~1.1 µs 固定地板）。§9（P15-1）在同一张 DAG 上对照三策略：`eager`（L 次 launch）/
`barrier`（单 cooperative kernel + 逐层 `grid.sync`）/`decen`（单 kernel + 设备侧原子 ready 队列 +
每 task 事件计数器，无全局屏障）：

- 均衡负载下 **`decen ≈ barrier ≈ eager`（0.99–1.02×）**；
- **小负载（每层 task 数 < block 数）`decen` 慢到 0.556×**——空队列 `__nanosleep` 自旋开销；
- 收益出现在 **task 多且异构**时：C=528≫G=132、段长伪随机 1–8×，`barrier` 仅 1.007×、
  **`decen` 1.167×**（对上 MPK §6.4 行 1551–1553 混合负载均衡动机）。

§15（P22-1）把「C 条链」推广到**分层扇入/扇出图**（L 层 × W 宽 × FIN 前驱），对照四机制
`barrier`/`wave`（层软屏障+原子计数）/`decen`/`static`（grid-stride+事件轮询）：

- **严格分层均衡图上集中式 `barrier` 恒最快**（`wave`/`static` 0.82–0.99×、`decen` 0.27–0.47×），
  层数增加（L 32→128）也不翻盘；
- `decen` 有**每 task 固定开销**：固定 W=512、把 task 长 SEG 4096→32768，`decen/b` 从 **0.278×→0.956×**
  （长 task 摊薄）；
- MPK §5.2 **批量取 task 的甜点 K≈W/G**（K=4 → 1.028×、K=16 骤降 0.530×）。

> **设计含义**：拓扑不是「越去中心越好」。**均衡 + 每层 task 多（W≥256）→ 集中式 barrier 最省**；
> **倾斜 / 混合 / task 细而多 → 去中心化事件驱动才赢**。生产 megakernel 选后者，是因为 LLM 的图恰好
> 是「深、倾斜、task 多」（MoE 路由、变长 attention），而非均衡分层。

## 3. ready 结构的容量与死锁（P42–P46）

有界 ready 结构（ring block / SMEM 页 / pool block）由**准入顺序**与**容量**共同决定死锁与吞吐。
本专题用五轮实验把它收口成两个**不同来源**的闭式。

### 3.1 图静态量：阻塞数 `B(π)` 与 `CAP* = G* = B(π)+1`

§31（P42-1）从 DeepGEMM 的两件防死锁机制出发（`scheduler/mega_moe.cuh:15-80`：`get_num_l1_warmup_waves()`
注释 *"ensure no L1 → L2 deadlock"*、`get_num_max_live_pool_blocks()` 的闭式 ring 上界）：单层 fan-in
下，**死锁边界 = 首个 m-block 的 consumer 数 `Kc`**（`CAP≤4` 死锁、`CAP≥5` 即活），`warmup(W=M)`
任意 `CAP` 全解；且**容量是吞吐硬下界**——`G=64` 扫 `CAP`，`CAP=2` 慢 **27.6×**、`CAP≥G=64` 饱和。

§32（P43-1）推广到**分层依赖 DAG**（L 层 × W × FIN）：边界 = **阻塞数 `B=(L-1)·W`**，且资源分量各自
富余时 **`CAP*` 与 `G*` 都精确 = `B+1`**（§32.3 升级为**(CAP,G) 联合约束**：`L=8`（B=112）必须
`CAP>B` 且 `G>B` 同时成立）。warmup 深度须覆盖**完整依赖深度**（`D≈L-1`）。

§33（P44-1）推广到**不规则 DAG**（宽度不等 / 跨层 skip / 多级扇入 / **层号乱序**），给出**普适量
`B(π)`** = 「沿准入 order 逐个准入、立刻排空任何前驱全 done 的 task，池内『已准入未完成』的峰值」，
实测 **`CAP* = G* = B(π)+1`**；`§31` 的 `Kc`、`§32` 的 `(L-1)W` 都是它的特例。两个反直觉点：
**`B` 不能简化成「第一个就绪 task 的位置」**（源在前、后面再堆满阻塞的形态会漏算）；**「按名义层号
升序」≠「拓扑序」**——层号乱序时须真拓扑线性化（Kahn），对照 MPK 依赖分析器（`docs/08` §5）。

### 3.2 排队量：有界环形缓冲的 `CAP_safe + G ≈ W_max + 1`

§35（P46-1）把事件驱动调度装进**有界 ready 环形缓冲 + 阻塞背压**，得到的容量下界**来源不同**：
`G ≤ W_max` 时 **`CAP_safe + G ≈ W_max + 1`**（`W_max`=最大层宽）——G 个 worker 在飞、环只缓冲宽层里
`W_max−G` 个未被取走的就绪 task。这与 §31–§34 的 `B(π)+1`（准入顺序/依赖深度决定的**图静态量**）
是两笔不同的账：**这里是「并发就绪数 ÷ worker 数」的排队量**。容量是**安全阀不是吞吐旋钮**：
`CAP≥CAP_safe` 后延迟完全持平（0.375 ms，差 <1%）。边界还有时序竞态（靠近边界时**单次可完成、
多次可能死锁**）。

### 3.3 零成本正解：事件驱动让 `G*≡1`

§34（P45-1）把 §33 的「依赖门控 `gated`」从**调度器扫描**换成 MPK §5.1 真机制——每个 task 一个
**事件计数器** `dep_left`（未完成前驱数），完成前驱的 worker 直接 `atomicSub` 并**把归零者 push 进
ready 队列**，scheduler 不参与准入：

- `raw`（不查就绪）复现 `B(π)+1`（`B=16` → `CAP=1` 死锁、`CAP=17` 活）；
- `scan`/`topo` `B≡0`；**`event` 更是在 `CAP=1` 且 `G=1` 即活**（ready 队列只装就绪 task）；
- `N` 扩到 4096：`scan/event` 1.3–3.0×（扫描随 `N` 变慢），`topo≈event`（0.95–0.98×）——两者都不扫描；
- 独立扫 `G`：`raw CAP*=G*=B+1`（须 `G>B`），**`event G*≡1`**。
- 扇入 `FIN` 2→16 抬高 `scan/event` 到 **2.4–3.5×**，`event` push 代价近持平。

> **设计含义**：**用事件驱动就地入队，有界池死锁在语义上根本不存在**（只准入就绪 task ⇒ 池内无
> 阻塞 task）。反过来说，若你选了「scheduler 集中准入 + 有界池」，就必须付额外代价：要么**预计算
> 拓扑序**（`topo`，吞吐无损但需依赖分析），要么**warmup 到完整依赖深度**（`D≈L-1`，见 §32/§43），
> 要么**把容量开够**（`CAP>B(π)`，但容量还是吞吐下界）。这三条正是 DeepGEMM 的
> warmup wave + 容量闭式的由来。

### 3.4 容量下界一览

| 来源 | 闭式 | 决定因素 | 是否吞吐旋钮 | 坐标 |
|---|---|---|---|---|
| 图静态（单层 fan-in） | `CAP* = Kc + 1` | 首个 m-block 的 consumer 数 | 是（`CAP<G` 饿 worker） | §31 |
| 图静态（分层） | `CAP* = G* = (L-1)·W + 1` | 层序几何 | 是 | §32 |
| 图静态（不规则普适） | `CAP* = G* = B(π) + 1` | 贪心峰值池占用 | 是 | §33 |
| 排队量（有界环） | `CAP_safe + G ≈ W_max + 1` | 并发就绪数 ÷ worker 数 | 否（安全阀） | §35 |
| 事件驱动 | `G* ≡ 1`，无 `B` | — | — | §34 |

## 4. 队列协议：内存序与多生产者

### 4.1 发布内存序（P47-1，§36）

本专题此前所有合成队列都默认 relaxed+侥幸。§36 用 litmus 试纸实测 sm90 的序画像：

- **store→store 保序、store→load 可绕过**：MP litmus relaxed **0/70M**（写→推未重排）；正对照
  SB litmus relaxed **100%（5M/5M×2）**（store→load 重排完全可观测，**证明试纸有效**）。
- 「先发布 tail 后写数据」在本机自然时序下 **0 错**，但人为拉长窗口的 `pubslp` **20000/20000 全错**
  ——「没出事」是**时序侥幸、非形式保证**；正确程序序 `wro`（无 fence）与 MPK 协议 `rel`（release/acquire）
  全 0 错。
- **release/acquire ≈ +0.36 µs/槽（几乎恒定）**：fence 是固定成本，大 payload（`PL=256`）摊薄后近免费
  （1.06×）。这正是 MPK「relaxed 写数据 + **单条** `atom.cas.release.gpu` 推游标」而非全程 fence 的理由
  （快照 `mpk_atoms.cuh:17-96`）。

### 4.2 多生产者与「连续放行」（P48-1，§37）

MPK 的 `sched_queue` 是 **MPSC**（128 worker / 16 scheduler ⇒ 8 生产者/队列），push 三步 =
**占位（`atom.add.release`）→ relaxed 写 payload → 连续 CAS 放行**（`persistent_kernel.cuh:1206-1228`）；
`worker_queue` 是 SPSC，单条 `atom.add.release`（`:1495-1502`）。§37 实测：

- 连续 CAS 放行（`mpk`）与逐槽 release 标志（`pertile`）在多生产者下**全对**；
- **决定性正对照 `stall0`**（低号槽 `r<4` 延迟 ~110µs）：非连续完成计数（`reserve_count`）与
  「占位即就绪」（`pub_then_write`）**`bad=8` 稳定复现（3/3）**，而 `mpk`/`pertile` 恒 0。
- ⇒ **MPK 第③步「连续 CAS 放行」是「占位乱序 ⇒ 必须连续」的必要工程**（SPSC 不需要）。

### 4.3 批量出队与多线程消费者（P49-1，§38）

§38 把 MPSC 队列升级为「批量出队 + 一个 warp 并行校验 + 128 B 真实 `TaskDesc`」：

- 批量/多线程出队**不动数值**（连续 CAS 游标保证「读到 `last_ready=c+K` ⇒ 前 `c+K` 槽已写」）；
- **单线程批量只收回「放行往返」**，约 1.2–1.5× 封顶；
- **多线程（warp）并行读描述符，128 B 下快 21×**（`serial` 随描述符线性变贵 ~170 ns/字，`warp` 几乎不变）；
  §D 拆因：`serial` 路由 1218 vs 全校验 6353（5.2×），**`warp` 路由 301 vs 303（几乎相同）**——**能否
  并行读 payload 是「路由型」与「全描述符型」消费的分水岭**。

> **设计含义**：队列协议的三条硬约束是 **① release 发布（不能只 relaxed）② 多生产者必须连续放行
> ③ 消费者要能批量/并行读 payload**。三条都被 MPK 与 DeepGEMM 的 ring generation 逐条实现。

## 5. worker 取 task：载体 × 预算 × 流水

这一层是 P50–P57（§39–§46），也是本专题最细的一层。被测对象：worker 怎么把 352 B 的 `TaskDesc`
（MPK §6.1 行 1365）从 global 搬进来（快照是**全线程协作 16 B `cp.async` 进 SMEM 单缓冲**
`cp_async_wait<0>`，`persistent_kernel.cuh:1063-1078`）。

### 5.1 载体：`cp.async` 的价值是「成本与描述符大小无关」

§39（P50-1）四取数路径对照 `scalar`/`vec4`/`cpasync`（SMEM 单缓冲）/`cpasync_pf`（双缓冲预取）：

- 小描述符（≤128 B）时 `cpasync` 反比 `vec4` 慢 1.15–1.44×；
- **到真实 352 B（`DW=88`）翻盘：`cpasync` 58.0 vs `vec4` 132.9（2.29×）、vs `scalar` 167.1（2.88×）**
  ——因寄存器读被寄存器压力拖垮，而 `cpasync` 从 128 B→352 B 几乎不动（55.7→58.0）。
- **预取（双缓冲）相对单缓冲稳定收回 7%–40%**（`K` 越小越多）。

§40（P51-1）扩到 **G 个 worker**：aggregate 带宽随 G **近似严格线性、到 G=264 仍未饱和**（取数是
**per-worker 延迟绑定**，带宽只能靠堆 worker 换）。**TMA bulk 单缓冲 ≡ 16 B `cp.async`**（省指令不改
吞吐），**收益全在双缓冲预取**：真实 352 B 下 `bulk_pf` **1263 GB/s**，比 `vec4` 快 **3.75×**。

§41（P52-1）/§42（P53-1）进一步把「双缓冲」推广成 **D 深环形缓冲（每槽 K 条）**，追问
**同等 SMEM 预算下大批量浅环 vs 小批量深环**：

- **环深 `D`：1→2 拿到全部预取收益、`D≥2` 完全平坦**（K=8：402.8→579.9 GB/s 后恒 ~580）；
- **吞吐单调取决于批量 `K`**（每批一次 mbarrier 等待 + 两次 `__syncthreads` 的固定开销摊到 K 条）：
  `K=1,D=186`（用满 64 KB）73.8 GB/s vs `K=64,D=2`（只用 44 KB）**2096 GB/s（28×）**；
  **最优 = 大 K + D=2**，深环是浪费。
- **载体高下随 `K` 翻转**（P53-1/§42 §B）：`K≤32` cp.async 反超 1.06–1.23×、`K=128` bulk 反超 1.07–1.13×
  （根因：cp.async 发指令条数随 K 线性增长，bulk 一条搬整批）。
- **「cp.async 释放寄存器」被否证**（P53-1/§42 §D）：`H=0` 时 `fetch_task_ca` **28** regs vs
  `fetch_task_reg` **19**——SMEM 寻址抵消了省；故 cp.async 的价值是「成本与描述符大小无关」+
  「**零寄存器代价预取**」，**不是**取数代码省寄存器。

### 5.2 取 × 执行：预取把描述符取数藏进 task 执行

§43（P54-1）第一次把「取 task」与**真正 task 执行**放进同一循环（`R`=执行时长旋钮）：

- **预取收益随 task 变长单调衰减、绝对收益恒定**：`D=1`（快照单缓冲）vs `D=3` 的 speedup 从 `R=0` 的
  **1.354×** 降到 `R=262144` 的 **1.003×**，而绝对差恒 ~**0.017–0.023 ms/run**（不随计算量放大）。
  **单缓冲多付的是一条固定长度的串行缝**（≈每 worker-batch 0.9 µs）。
- **决定性分解**：`D=3 = max(fetch_only, exec_only)`（`p/max` 1.001–1.047）——**预取把描述符取数
  完全藏在 task 执行后面**；`D=1`（快照单缓冲）始终落在 `exec_only + ~0.02 ms`。

§44（P55-1）/§45（P56-1）/§46（P57-1）把「吃 HBM 的 task 执行」接上，回答「取数与执行是否争带宽」：

- **几乎不争**：`D=2` 全程趋 `max(fetch,exec)`、从不接近相加；`EDW=4096` 数据面已饱和（~3007 GB/s）时，
  预取只比纯执行慢 **1.5%**——控制面钻的是数据面没吃满的 ~10% HBM 余量。
- **数据面与控制在「每 block 线程数」上最优相反**：数据面读带宽随 `T` 上升、**`T=1024` 饱和到 ~2983 GB/s**
  （≈ H100 HBM3 峰值 ~89%），而**控制面 `fetch_only` 取数带宽随 `T` 下降**（`T=256→1024` 由 1791→891 GB/s）。
- 这个矛盾**可用多 block/SM 化解**（P57-1/§46 §B）：数据面饱和的旋钮是「**每 SM 总线程数**」而非
  「`blockDim`」——`B=4,T=256`（3009）≥ `B=1,T=1024`（2928）；**控制面取数高度依赖 `K`、对占用率较不敏感**
  （`K=8/16/32/128` = 437/691/937/1782 GB/s）。⇒ **数据面认「总线程/SM」、控制面认「K」两个正交量**，
  设计上「用多块凑 1024 线程/SM、把 K 尽量做大」，二者在 SMEM 预算内可同时满足。

> **设计含义（取 task 层）**：**载体**在真实 352 B 下选 `cp.async` 或 TMA bulk（都「成本与大小无关」）；
> **批量 K 要尽量大（≈32–128）、环深 D=2 就够**（预取收益 1→2 一次拿完）；**预取缝是固定长度、
> 重 task 下可完全藏住**，故「多而薄」的 MPK task（293→13867 task，`docs/01` §3）**比**「少而重」的
> DeepGEMM 段级 task **更需要** pre-fetching（论文 §5.3 行 1364-1368）。

## 6. 描述符来源：预计算 + 调度 vs 设备现场生成（P58–P65）

§47（P58-1）把「描述符来源」接进同一流水，拆成两个正交成本——**调度**（预计算描述符 + 设备只推就绪）
vs **生成**（设备现场造 352 B payload）：

- **差 ~27×**：`static` 0.1605 ms（862.5 GB/s）/**`sched` 1.3614 ms（8.48×）**/**`gen` 36.489 ms（227.4×）**；
- `gen` 的瓶颈是**单 SM 标量写吞吐**（与 `G` 无关）；`sched` 的额外计算**直接显形**（决策成本）。
- ⇒ **megakernel 的「动态」必须落在调度（推 task id），不能落在生成 payload**——正是 MPK
  （`runtime.cc` 预计算 `FullTaskDesc`、scheduler 只做事件→id 映射）与 DeepGEMM（编译期静态角色）的做法。

§48（P59-1）把单块 producer 扩成 **P 块**：`sched` **撞「静态读地板」**（P=1 的 1.32 ms → P=32 的
0.262 ms 后不再降），**P=16=0.275 ms 正落 MPK 的 16 scheduler SM 量级**（把 §47「单块 sched 上界」
钉成实测）。§49–§50–§51–§52–§53–§54 逐层追问「现场生成」能不能追上：

- **写入形态**（§49）：逐线程 `uint4` 在 P=1 把 `gen` **36.58→10.49 ms（3.5×）**；瓶颈是 **store 发射/
  指令吞吐而非 DRAM 写带宽**（单 SM 3.8→13.2 GB/s）；整机写天花板 **标量 ~207 → v4 827 → coop 875 GB/s**。
- **TMA bulk store**（§50）**证伪「接上最宽写载体就能追平读」**：任何 P 下 TMA store 都不超过 16 B 寄存器
  store；两跳上限（reg→SMEM→global）766 GB/s。
- **正确握手税**（§51/§52）：写端瓶颈**不在 store 引擎、不在完成等待（拆掉只 +7%），而在「每批发布一次
  跨 SM 进度」**——`st.release head` + 背压门 `ld.acquire tail`，且**两者同时存在才昂贵**（单拆任一个都回 664）。
  §52 逐相位 + SASS 钉死：`st.release.gpu` 落成 `MEMBAR.ALL.CTA → MEMBAR.ALL.GPU → ST.E.64.STRONG.GPU`，
  每批把该 SM 访存流水 order 一次；**贵的是 release store，不是 acquire/fence**。
- **换写载体不改结论**（§53）：三载体（TMA store / 寄存器 copy-out / 寄存器直写）上 §52 的 L 型加性、
  release 主导**逐档同形**，但**快载体相对罚更狠**（`ser→nobp` 落差 29.9%/33.6%/36.8%）。
- **端到端**（§54）有界环绑定时，**背压×容量的乒乓往返主导（~20×）**，内存序税被完全盖过；**把窗开够大/
  批量取，比重写单条 release 重要一个量级**。

> **设计含义（描述符来源层）**：**「预计算 + 读」是描述符通路唯一可行形态**。设备现场生成即使上向量化
> （3.5×）、协作写、最宽写载体，仍比预计算读贵一个量级，且要吃生产者 SM、还引入 release 簿记税。
> 这条给 MPK 的 AOT/编译期预计算与 DeepGEMM 的静态角色以**更强**的量化理由。

## 7. 环协议与预取深度：`D` 不是自由旋钮（P66–P69）

§55–§58（P66–P69）把「worker 取 task」的**预取深度 `D`** 与**环协议/分配形态**量到底：

- **`D` 的纯性能上限小且立刻饱和**（§55 §D）：无生产者 worker 地板 `D=1→2` **+19%**（EDW=0）、
  `D=2` 精确饱和；
- **接入动态生产者 + 有界环后 `D>1` 语义不可得**（§55 §C）：紧环下 strided `D>1` **死锁**、
  contig `D=1..8` **静默数值错**却"更快"（错误形比死锁形更隐蔽）；唯一正确形态是 **strided + D=1**；
- **根因是「共享前缀 `tail` 计数器」**（§55 §E）：worker/producer 边界不对齐（`chunk≠bp`）时 producer 被
  两个 worker 并发消费、`tail` 越过未消费/在飞 slot 被覆写；
- **换成每槽回收**（§56/P67）连续分配**不再错**，但**解锁的是正确性不是性能**（contig 正确档慢 3–3.5 vs
  strided 17 GB/s）；且 per-slot 把 strided 的门**收紧**到 `CAPp≥bp`（与 `D` 无关）。
- **每 worker 独立环（一消费者一环）**（§57/P68）：`pair` 在 `D=1..4` 全部 OK，且 clean control 下
  `pair` 比共享缓存 **1.45×**（去掉跨 worker 前缀计数器争用）；**阈值精确 `CAPp* = D`**。
- **真实 MPK 形态：少 producer × 多 per-worker 环**（§58/P69）：把「环所有权」与 block 解耦，
  **一个 producer 轮转填连续一段 worker 环**（`grid=PS+G`）。结论：
  - 解锁是**拓扑性质、与 producer 数无关**（`PS×D` 32/32 OK，阈值仍是 per-ring `CAPp*≥D`）；
  - **喂饱 G 个 worker 所需的 producer 数 `PS*` 随 task 计算重量 `CW` 单调下降**：
    `CW=0` 需 `PS*≈G`（描述符带宽主导，单 producer SM ~4.2 GB/s），`CW=2^16→PS*=8`、`CW=2^18→PS*≈4`；
    重 task 下 **`PS*:G ≈ 1:25`，正对上 MPK 的 4 scheduler SM : 128 worker SM（1:32）**。

> **设计含义（环协议层）**：**`D` 不是自由的性能旋钮，而是被环协议锁死的自由度**。要用 `D>1`，
> 前提是「**一消费者一环**」（前缀计数精确，MPK `per_worker_queue_len` 正是此形）；若共享一个全局环，
> 就必须改协议（每槽独立回收/就绪 = DeepGEMM ring generation 逐槽发布）。而 `PS*` 只由 task 轻重决定——
> **重 task（真 GEMM/attention）下几个 scheduler SM 即可喂满整机 worker**，轻 task 才需要 ≈G 个 producer。

## 10. 回到 MPK / DeepGEMM 的印证

把上面六层结论对着生产实现看，几乎逐条命中：

- **角色划分**（部件 1）：MPK 4 scheduler SM : 128 worker SM = 1:32（§5 行 1157–1164、§6.2 行 1460），
  正落在 §58 量出的「重 task 下 `PS*:G≈1:25~1:32`」区间。
- **per-worker 环**（部件 2/6）：MPK 每 worker 一条独立队列（快照 `per_worker_queue_len=8192`
  `persistent_kernel.cuh:1790-1791`、§5 行 181 *"Each worker maintains a dedicated task queue"*），
  正是 §57/§58 的「一消费者一环、前缀精确、少 producer 轮转填」。
- **事件驱动**（部件 3）：MPK §5.1 完成者直接通知 event（`docs/04` §34 的 `event` 模式；`docs/06` §3
  设备侧 worker/scheduler 循环），即 §34 的 `G*≡1`。
- **内存序**（部件 4）：MPK「relaxed 写数据 + 单条 `atom.cas.release.gpu` 连续放行」（`mpk_atoms.cuh`、
  §37）即 §36/§37；DeepGEMM Mega Gate 的 `red.async.inc.release` + 无符号距离 wait
  （`scheduler/mega_gate.cuh:13-39`）是逐槽 generation 版。
- **预取**（部件 5）：MPK §5.3「Pre-fetching task descriptions」（行 1364-1368）即 §43 量出的
  「把固定串行缝藏进执行」——对「多而薄」的 MPK task 尤其必要。
- **预计算**（部件 6）：MPK `runtime.cc` 预计算 `FullTaskDesc`、scheduler 只做事件→id 映射，
  DeepGEMM 编译期静态角色 + 容量闭式（`scheduler/mega_moe.cuh:47-80`）——即 §47/§48「动态必须落在
  调度、不能落在生成」。
- **防死锁**（部件 2）：DeepGEMM `get_num_l1_warmup_waves()` 注释 *"ensure no L1 → L2 deadlock"*（`:15-45`）
  + `get_num_max_live_pool_blocks()` 容量闭式（`:47-80`）——即 §31/§32/§33 的 `B(π)`/warmup/容量三条。

## 11. 局限

- **绝对吞吐对 codegen 敏感**：§58.7 明记本 harness 与 §57 同逻辑映射互差 ~1.2×（DRAM/L2 与屏障停顿
  差异）——跨源码的 `descGB/s` 只可作定性对照。
- **描述符是合成的**：内容为 `gen_word` 折叠，非真实 GEMM/RMSNorm；`CW` 是纯 ALU 延迟，只拉长 task、
  不产生真实 HBM 流量，`PS*`-vs-`CW` 曲线**形状可信、拐点只对本微基准成立**。
- **判据普遍停在 C4**：§31–§58 的装置都是单常驻 kernel、scheduler/worker 角色分离，但 worker 仍静态
  分配 batch，**均「仍差 C5 一步」**——真正跑起动态 worker/scheduler 派发的是 §9（P15-1）的最小
  骨架（C1–C5 全满足，但只在均衡 DAG 上验证）。
- **未与 DeepGEMM SM100 路径对跑**：DeepGEMM mega 家族是 SM100 专属，本机 H100/sm90 不具备
  （每节都明记）。
- **有些数字是合成口径**：如 §52 的 SASS 计数是整 kernel 而非限定基本块、纯写口径无 worker。
