## 1. 数据面能到多快、要多少 producer（§59–§61）

### 1.1 `PS*` 随 task 重量反向（§59，P71-1）

把 §58 的 worker 加上一条**真实 HBM 数据面**（每 batch `__ldcs` 流式读 `MD` 个 `uint4`），量「喂饱 `G`
个 worker 所需 producer 数 `PS*`」随**访存重量**的曲线（源码 `src/sched_perworker_ring_mem.cu`）：

- **`PS*` 随访存重量 `MD` 单调下降**：`MD=0/8192 → PS*≥32≈G`（≈1:1）、`MD=32768`（512 KB）
  **`PS*=16`（1:6.25）**、`MD=131072`（2 MB）**`PS*≈4`（1:25）**——**与 §58 的纯计算重量 `CW`
  同族、对上 MPK 的 **4 scheduler SM : 128 worker SM（1:32）**（`docs/01` §5 行 1157–1164、§6.2 行 1460）。
- **两笔重量同向叠加**：`CW=65536` 单独 `PS*=16`，叠加 `MD=32768` 后 `PS*=8`。
- **控制面不争 HBM**：achieved 数据面带宽随 `PS` 只升不降（650→952 GB/s），producer 写描述符
  （~5 GB/s）可忽略——**控制面瓶颈在握手 MEMBAR / 会合，不在 HBM 带宽**（与 §52–§54 互为印证）。
- **局限**：数据面只到 ~950 GB/s（单累加器依赖读、低 MLP），**未把 HBM 推到饱和**，故「不争用」只在
  远低于峰值区间成立（→ §60 补）。

### 1.2 数据面饱和度是「设计量」不是「硬件量」（§60，P72-1）

给数据面加**内存级并行度 `U`（ILP 展开因子）**，把数据面推到饱和（源码 `src/sched_dataplane_sat.cu`）：

- `T=256`：`U=1→2` 把数据面从 **926→1490 GB/s**，`U=16` 达 **2218**——**§59 的 ~950 是「单累加器依赖链」
  的产物，不是数据面固有**。
- `T×U` 矩阵：`T=1024,U=4` 与 `T=512,U=16` 都到 **~2840 GB/s**（H100 峰值 3.35 TB/s 的 ~85%）——
  **饱和由「每 block 在飞字节 `T×U`」定**。
- **闭合 §59.6 的争用问题**：饱和配置下 `mode0`（无 producer）**2792** vs `mode1`（`PS≥8`）
  **2763–2837**——**饱和点上加 producer 仍不拖慢数据面**；`PS*≈8`（比 §59 的 4 高，因数据面快了 ~3×）。

### 1.3 数据面到真峰值 + 控制面争用（§61，P73-1）

把数据面从调度骨架里**抽出来单独量**（纯读微基准，源码 `src/dataplane_peak.cu`）：

- **数据面到 ~3219 GB/s = HBM3 峰值 96%**（寄存器 `__ldcs` 载体、`T=1024`、2 block/SM、`U=4`）——
  比 §60 的 2840 快 1.13×；**缺的旋钮是占用率**（§60 卡在 1 block/SM = 50%）。`__launch_bounds__(1024,2)`
  把 `U=4` 的 40 regs 压到 32、1→2 block/SM。**ILP 与占用率是替代品**。
- **TMA bulk 载体也够**：~**3075 GB/s**（寄存器峰值的 96%、绝对峰值的 92%），但**用更少寄存器**
  （`DC=2048` 用 32 regs→2 block/SM，寄存器 `U=4` 要 40）——**TMA 的价值在省寄存器而非更快**，
  对上 MPK worker 用 TMA 搬 tile（`docs/07`）。
- **真峰值下「描述符写不争 HBM」结论变弱**：读带宽随写速率**超线性**下降——`write=21.7 GB/s`（占读 0.7%）
  读降 **7.9%**、`78.6`（2.6%）读降 **16.7%**（HBM **bus turnaround**，非字节比账）。**§59.6/§60.5 的
  「不争用」是「读余量」的函数、不是字节比的函数**；生产描述符流量 ~15 GB/s（~0.5%）落在读降 3–7% 档。
- 判据：微基准 **C1**、多算子数据面形态；**未含设备内调度**，故只是给 §47–§60 的 C1–C4 骨架配一张
  **数据面能力表**。

## 2. 端到端骨架的夹层成本（§62–§63）

### 2.1 同一二进制内三档剥层（§62，P74-1）

把 §61 的**占用率旋钮**搬回 §60 的**完整骨架**，在同一二进制内用 `mode ∈ {data-only, +fold, full}`
逐层剥开（源码 `src/e2e_saturation.cu`）：

- **同二进制数据面天花板 ~3156 GB/s = 峰值 94%**；抬占用率两条等价路径：`T=256` 加大 `G`
  （100→1040：974→3138），或 `T=1024,U=8`（`G=100` 即 3063）。
- **端到端 full 骨架 `G` 越大反而越慢**：`T=256` 路线峰值仅 2058（G=528）、G=1040 降到 1768；
  `T=1024` 路线 2831（G=100）→1910（G=1040）。**端到端最优不是满占用率**，而是 §60 的**「少而大」worker
  块**（`G=100,chunk=21,T=1024,U=8` = **2831 = 85%**，精确复现 §60）。
- **夹层分解**（headline）：`G=1040`：data-only 3139 → +fold 3105 → full 1761（**fold −1.1% 几乎免费，
  环+producer −43.9%**）；§60 配置 3078 → 3118 → 2913（fold +1.3%，环+producer −6.6%）。**§61.10 把 gap
  猜成「取 task/折叠」是错的，真正的成本是控制面（环协议 + producer）且随 `G` 恶化。**
- 定位：`G=1040` 扫 `PS` 1→32（343→**2500**，仍升）、扫 `chunk` 2→8 只 +3.6%（**每 task 开销不是瓶颈**）
  ——成本来自**「少 producer 轮转服务多 per-worker 环」的扇出**。**正确设计压力是调度器服务速率，不是
  纯并行度。**

### 2.2 producer 服务模型：扇出归因被证伪（§63，P75-1）

把 §62 的 producer 写端**单独抽出来**（无 worker / 无背压 / 无数据面），唯一变量 = 每个 producer 连续
服务的**环数 `wpp`**（固定每 producer 总批数，源码 `src/producer_service_model.cu`）：

- **固定每 producer 工作量，吞吐不随环数下降**：`PS=32,Btot=64`，`wpp=1→64` 吞吐 **158.2→166.0**（略升
  后平台）、`cyc/batch` **4336→4126**（±2.5%）——**不存在可测的「每环服务成本」**。
- **成本结构是纯每批**：`wpp=1` 扫 `Btot`，`cyc/batch` 恒 ~4335–4357。`PS=1→32` **精确线性**
  （5.2→165.1 GB/s，每 producer ~5.2 GB/s，无跨 producer 争用）。
- **加回 plain-load consumer 也只加一笔固定开销**：`PS=8,NB=2048` 扫 `R`——producer-only 恒 42.6–42.7、
  +consumer 只降 ~12% 且**同样平**（37.3–37.4），**不随环数放大**。
- **结论/修正**：producer 服务成本 = **每批一次 `fence+st.release`+两次 `__syncthreads`**
  （`cyc/batch≈4135–4357` ≈ **~2.1 µs**、单 SM 描述符天花板 **~5.2 GB/s**，对上 §52 的 release 税）。
  **§62.7 的「producer 环扇出」归因被隔离证伪**——§62 的「`G` 越大越慢」只能住在 **worker 侧**或其
  **占用率/共驻**里（→ §64/§65 定位）。

## 3. worker 侧复杂度阶梯与取 task 载体（§64–§66）

### 3.1 `G` 依赖 = 每 block 一笔固定 prologue（§64，P76-1）

把 TMA + 折叠 + 数据面按 §62 加回（worker 侧复杂度阶梯 `wmode`，源码 `src/worker_side_attribution.cu`）：

- **复现 §62**：`tma+d` 1740@G=1040（§62 报 1768，<2%）；相对 `data-only`（3076）跌 **−43.4%**；
  `plain ≡ tma`（无数据面时都被 `PS=8` producer ~31 GB/s 钉住）——**§63 的「consumer 平」是被 producer
  盖住、不等于免费**。
- **拆出闭式**（固定 `chunk=4`、`NB=4·G`，折成每 block）：**环消费者 prologue ≈ +0.35 µs/block（plain
  就付）**、**TMA 取 task 额外 ≈ +0.3 µs/block（tma 合计 ~0.69）**，**跨 `G=100..1040` 恒定**
  ——**§62 的 `G` 依赖 = worker 侧每 block 一笔固定 prologue**，`chunk` 越小越显形，TMA 把它翻倍
  （`chunk=4` 下 `G=1040` full 从 1740 抬到 2083）。
- 固定 `G=264` 扫 `MD`：`MD=0` 时 plain ≡ tma，数据面一上来 **plain 比 tma 快 4–6%**——TMA 的代价只在
  快路径上可见。

### 3.2 第三种载体 `cp.async`：TMA 的 prologue 是 TMA 专属（§65，P77-1）

把 MPK worker **原生**的取 task 载体（16 B `cp.async` 单缓冲进 SMEM，快照
`persistent_kernel.cuh:1063-1078` 的 `cp_async_wait<0>`）加进 §64 阶梯（源码
`src/worker_carrier_cpasync.cu`）：

- **`cp.async ≡ plain`、TMA 随 `G` 掉队**：固定 `NB=2048` 扫 `G`，`ca/plain` **0.99–1.01×**；
  `tma/plain` 从 `G=132` 的 0.969 掉到 `G=1040` 的 **0.813×**。
- **TMA 的 +0.3 µs/block prologue 是 TMA 专属**：固定 `chunk=4` 折成每 block——`tma−plain` 恒
  **+0.25…+0.32 µs/block**（复现 §64），而 `cp.async−plain` 恒 **−0.04…+0.005 µs/block（≈0）**。
  **TMA 的 setup（`mbarrier.init ×D`+`arrive.expect_tx`+首次 `cp.async.bulk`+`mbar_wait`）不是
  「用 SMEM 取 task」的通性。**
- 固定 `G=132` 扫 `chunk`：`chunk=1` 三载体相等；`chunk≥2` 起 `cp.async ≥ plain > TMA`，都随 `chunk`
  增大向 `data-only` 收敛。
- **解释 MPK 为何用 16 B `cp.async` 而非 TMA bulk 取 task**：常驻 worker 每 SM 付一次 fetch setup，
  cp.async 的 setup 比 TMA 轻 ~0.3 µs/block；TMA 的价值在**载入 task 单体 tile**（§39/§42/§61/§62），
  **不在取 task 描述符**。

### 3.3 深环 cp.async 没有收益（§66，P78-1）

把 cp.async 从单缓冲升级成 **`DCA` 槽软件流水深环**（源码 `src/worker_carrier_cpasync_ring.cu`）：

- **深环没有任何一个点快过单缓冲**：`ca-single ≡ plain`（±1%）；`DCA=2` 掉到 ≈ TMA 档、`DCA=4` 更差。
  §G（`G=132,chunk=8`）扫 `DCA=1..8` **单调变慢**：1206→1136→1041→893 taskGB/s。
- **两笔净成本**：逐批**槽复用 `__syncthreads()`** + **SMEM 足迹随 `DCA` 线性增长**拉低占用率
  （`DCA=2`→8、`DCA=4`→5、`DCA=8`→2 blk/SM）。
- **为什么 §42 的「预取增益全在 D=1→2」不迁移**：§42 是**裸取数**（无数据面、无 producer 背压），
  `wait_group` 缝直接暴露；端到端里 352 B/task 取数**已被 HBM 数据面与 producer 就绪等待藏住**，
  **无缝可回收**。**再次确认 MPK 用 16 B `cp.async` 单缓冲是经过取舍的选择。**
- **口径 caveat**：本版内核描述符×数据面重叠被 ptxas 调度得比 §65 差（plain `localB=8` 有 8 B 局部溢出、
  `G≤132` 慢 ~1.6×），故**只采信同一二进制内的相对排序**（→ §67 归因）。

## 4. 寄存器预算 × 占用率 × 每块线程数 × ILP（§67–§70）

### 4.1 8 B 溢出的归因：寄存器预算，不是载体分支（§67，P79-1）

把 `__launch_bounds__(256,MINB)` 的 `MINB` 当**寄存器预算旋钮**（源码沿用 §66 内核 + `regs` 子命令）：

- **溢出归因**：`MINB=8`（32-reg 上限）下 plain / TMA 各 `localB=8`，`cp.async` 单缓冲与深环 `localB=0`；
  放宽 `MINB` 后 plain 到 **`MINB=4`（52 regs）**、TMA 到 **`MINB=6`（40 regs）** 才干净
  ⇒ **8 B 溢出是 32-reg 上限打的，不是「运行期分支选择载体」**。**载体寄存器耐压序**：
  `cp.async` 单缓冲/深环（≤32）> TMA（~40）> plain 直接读（~52）——**直接读最耗、SMEM 载体最省**。
- **修正因果**：溢出**不是** §66 plain 慢的原因——`MINB: 8→6→4` 把 plain 在 `G=100/132` 提速
  **1.64×/2.43×、1.59×/2.14×**，但**一直 `localB=0`** 的 `ca1` 与 plain 逐点重合 ——主导量是
  **寄存器预算 → 数据面 ILP**，与载体正交。

### 4.2 单变量隔离：同占用率下多给寄存器快 1.70×（§68，P80-1）

用**两个独立旋钮**把「寄存器预算」与「占用率」拆开：占用率由 `grid=numSM·O` 钉死、寄存器预算由 `MINB`
钉死（纯读 `uint4` 微基准，源码 `src/reg_occ_decouple.cu`）：

- **§B（headline）**：`O=1`（`resident=1` 三档完全相同）下 `MINB=8`（32 regs）**1668.7 GB/s** vs
  `MINB≥6`（40–44 regs）**2847.2 = 1.70×**；`O=2` 1.21×、`O=4` 1.03×。**数据面认的是每线程在飞 load 数
  （寄存器预算撑起的 ILP），不是占用率本身。**
- **§C 替代品**：32-reg 预算靠占用率 `O=1→4` 补回 **1.83×**（1670→3060）；≥40-reg 预算 **`O=2` 即饱和**
  （2844→3163→3166）——给出 §60/§61「ILP 与占用率是替代品」的**机理**（都在供「每 SM 在飞 load 总量」）。
- **§E 载体免疫**：`cp.async` 单缓冲在固定 `O` 下扫 `MINB` **逐点相同（<0.2%）**（其自然寄存器 31–32 < 32
  上限）——**SMEM 载体在低寄存器预算下严格占优**。
- 判据：纯数据面微基准，**C1–C5 全不满足**。

### 4.3 精确寄存器上限：连续斜坡 + `T` 补回（§69，P81-1）

用 **`__maxnreg__(R)`**（PTX `.maxnreg`）把每线程寄存器上限设成**精确**值（源码 `src/maxnreg_decouple.cu`）：

- **§B（Q1）**：`R≤44` 时 `numRegs≡R`；§68 的 **1.70×** 如实复现，但**分界不是二元跳变而是连续斜坡**：
  32→36→40 = **1668.6→2137.1→2841.8** GB/s（36-reg 已收回 ~41% 的差），40 起饱和——**修正 §68.3 的
  二元措辞**。
- **§C（Q2）**：精确 `__maxnreg__` 与 `__launch_bounds__` 在匹配 `numRegs`（32/40/44）下**逐位等价
  （<0.3%）**——决定吞吐的是寄存器**数**本身。
- **§D（Q3 headline）**：固定 `O=1`、固定 `R` 只扫 `T`：`R=32` 从 `T=128→1024` 单调升
  **899→3136 GB/s（3.49×）**，`R=32,T=1024`（3136）≈ `R=64,T=1024`（3191，仅差 1.7%）
  ——**每线程寄存器预算与每 SM warp 数是替代品**（都供「每 SM 在飞 load 总量」）。
- 判据：**C1–C5 全不满足**。

### 4.4 `T`×`O` 二维面：饱和区只认合量 `O·T`（§70，P82-1）

在**固定寄存器预算** `R` 下同时扫 `T` 与 `O`（源码 `src/t_occ_surface.cu`）：

- **§E（headline）等积塌缩**：`O·T≥1024` 起**塌缩成单变量**——`O·T=1024` 的 12 个配置
  （`R=32/40/44` × `T=128/256/512/1024`）全落 **3045–3198 GB/s（极差 1.05×）**、`O·T=2048` 的 4 个落
  **2995–3181（1.06×）**——**饱和区吞吐只由 `O·T` 决定，与 `(T,O)` 拆分、与 32 vs 40/44 regs 无关**。
- **未饱和区寄存器预算仍是先决条件**：`R=32` 相对 `R=40/44` 在 `O·T=128/256/512` 落后
  **2.16×/1.76×/1.24×**——寄存器预算决定「达到饱和所需的最小 `O·T`」。
- **§F 两个天花板**：线程面 2048（仅 `R=32` 可达）、寄存器面受**分配粒度**影响——`R=32→2048 线程`、
  `R=40→1536`、`R=44→1280`（`R=64` 被自然需求封顶成 44 regs，复现 §69）。
- 判据：**C1–C5 全不满足**。

> **对 megakernel worker 块设计的含义**：一个轻 task 若因与最重 task 共处一个 kernel 被钉在低寄存器
> 预算（`docs/04` §8/§68），要收回数据面带宽只有一条路——**把该 task 的每 SM 线程数 `O·T` 抬到约 2 倍**
> （更多 resident 块或更大 `T`），且这条补偿的**上限是同一 HBM 面 ~3200 GB/s**。真正补不回的，是
> **「单 warp 深流水」型 task**（需要长 latency 隐藏的串行链）。

## 5. 把 §59–§70 收回一张决策表

| 决定 | 推荐 | 反例 / 代价 | 证据 |
|---|---|---|---|
| 多少 producer 喂 worker？ | **task 越重越少**：访存型 `MD=2 MB→PS*≈4`、对上 MPK 4:128 | 轻 task 需 `PS*≈G`（1:1）；数据面越快需越多（§60 `PS*≈8`） | §59、§60 |
| 数据面能到多快？ | 抬 **每 block 在飞字节 `T×U`**（ILP 与占用率是替代品） | §59 的 ~950 是低 MLP 产物，非硬件；饱和仍 ~96% 峰值 | §60、§61 |
| 端到端最优占用率？ | **「少而大」worker 块**（`G=100,chunk=21,T=1024,U=8`=85%） | 满占用率（`G=528~1040`）反降到 53–62%，因控制面扇出 | §62 |
| 端到端的成本是谁？ | **控制面（环协议+producer），不是 fold / 取 task** | fold 几乎免费（±1%）；§62.7「producer 扇出」被隔离证伪 | §62、§63 |
| worker 每 block 有固定开销吗？ | 有：**plain ~0.35 µs/block、TMA ~0.69 µs/block**，与 `G` 无关 | `chunk` 越小越显形 | §64 |
| 取 task 用哪个载体？ | **16 B `cp.async` 单缓冲**（= plain，setup 最轻） | TMA 每 block 多 ~0.3 µs；深环 `DCA>1` 单调更差 | §65、§66 |
| 寄存器预算怎么定？ | 设成 **`U` 所需自然需求**（`R=32` 是多数 task 不 spill 下界） | 多给寄存器只砍占用率；低预算用 `O·T` 约 2× 补回 | §67–§70 |
| 低寄存器预算的补偿？ | 抬 **每 SM 总线程 `O·T`**（或 ILP `U`） | 上限同一 HBM 面 ~3200 GB/s；深流水 task 补不回 | §68、§69、§70 |
| 精确压寄存器？ | 用 `__maxnreg__(R)`，与 `__launch_bounds__` 同 `numRegs` 等价 | `R≥` 自然需求时封顶失效（=上限非设定值） | §69 |

## 6. 回到 MPK / DeepGEMM 的印证

- **16 B `cp.async` 单缓冲取 task 是三重复合最优**：§65（setup 最轻 ~0.3 µs/block < TMA）、§66（深环
  只在裸取数有用、端到端无缝可回收）、§67（寄存器耐压序里自然需求 ≤32、免 `MINB` 溢出）
  ——三条独立证据同指 MPK 快照 `persistent_kernel.cuh:1063-1078` 的载体选择。TMA 的价值在**载入 task
  单体 tile**（`docs/07` §1 的 `linear_hopper`），不在取描述符。
- **4 scheduler SM : 128 worker SM 有量化依据**：§59（访存型重 task `PS*≈4`）、§60（数据面越快 `PS*`
  略升）、§58（纯计算重 task `PS*:G≈1:25~1:32`）三线合拢到 MPK 的 **1:32**（`docs/01` §5 行 1157–1164）。
- **「描述符预计算 + 只推 id」是唯一可行形态**：§61 真峰值下描述符写会以 3–7% 拖慢数据面（bus
  turnaround），而 §63 证 producer 每批成本是一笔固定的 release 税（~5.2 GB/s 单 SM 天花板）——
  MPK/DeepGEMM 用**极少 scheduler SM 推 id、不造 payload**（`docs/11` §6）恰把控制面流量压到不显著。
- **worker 块「少而大」是端到端结论**：§62 的 full 骨架最优不是满占用率而是 `T=1024,U=8,G=100`
  （85%），§64 把 `G` 依赖定位到每 block 固定 prologue——生产 mega-kernel 用 **warp specialization +
  少数重 task**（`docs/02` §1）正是避免「多而杂」的每 block 开销。
- **寄存器是 megakernel 唯一不可分页的资源**（MPK §7 行 1740–1748，`docs/04` §8）：§67–§70 从
  数据面侧补上「为什么」——寄存器预算决定「达到饱和所需的最小 `O·T`」，故异质 task 融合时轻 task 会因
  最重 task 被钉在低预算、须靠更高占用率补偿（上限 ~3200 GB/s）。

## 7. 局限（诚实标注）

- **§59–§66 是合成骨架**：per-worker 环 + producer 写**合成描述符**（`gen_word`）+ `__ldcs` **合成
  数据面**（非真实 GEMM tile / dispatch gather），拐点位置只对本微基准成立。
- **§67–§70 是纯数据面微基准**：无环协议 / 无 task 描述符 / 无调度器，**判据 C1–C5 全不满足**——它们
  度量的是 megakernel **worker 侧的数据面能力**，不含调度机制（调度机制由 `docs/11` 覆盖）。
- **只测目标卡 H100 / sm90、sm90a**：未与 DeepGEMM 的 SM100 专属 mega 路径对跑（每节都明记）。
- **绝对值对 codegen / 同机争用敏感**：§66.9 的跨二进制偏移、`G≤132` 的 HBM 争用抖动，故多处只采信
  **同源码族 / 同一二进制内的相对排序**；`O=1` 绝对值受同机其它任务影响（min-of-3）。
- **固定配置的窄口径**：多节固定 `U=4`、`R=32`、`T=256`；`O·T` 只到 H100 硬限 2048；`R` 有效精确档只
  32/36/40/44（§69 自然需求封顶）；未扫 strided / 非对齐访存模式（该维度由 `docs/12` §71 起覆盖）。
