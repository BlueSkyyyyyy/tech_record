# indexer 打分的粗筛-精排两级精度：2× 带宽省下来的排序精度几乎能全补回来

> 本篇是「DeepSeek Mega MoE 前向 / 反向算子实现解析」专题的增量（P167-1）。
> 承接第 171 篇（`docs/171`）与第 174 篇（`docs/174`）：第 171 篇量到 indexer 的 top-k 选择在量化下
> 会翻（FP8 recall 0.966、MXFP4 0.851），第 174 篇把 Q 与 KV 拆开、发现 **KV 是带宽主导项**
> （占字节 ~89%）、**KV 换 MXFP4 让总字节降到 0.55×**、但 recall 掉到 0.85。
> **两篇都把打分当成「单级、均匀量化」**：要么全 C 个 KV 都读 FP8、要么都读 MXFP4。
>
> 生产里 indexer 打分是**「扫全上下文 C 个 KV、取 top-k」**。本篇问一个工程问题：
> 与其把这一次扫描**均匀压到 MXFP4** 省一半字节（但丢排序精度），能不能**拆成两级**——
> 先用便宜的精度**扫完 C** 拿到一个稍大的短名单 M，再只对 M 个**用高精度重算**？
> 也就是「**全读低精**」换成「**少读多精**」。
>
> **结论**：能。在真实 SM90 `fp8_fp4_mqa_logits` 锚定的打分上，
> **两级级联用 0.5625× 的字节就把 FP8 级 recall（0.9612 vs 0.9616）补回来**——
> 只比均匀 MXFP4（0.50×、recall 0.8743）多花 **12.5% 字节**，却换回 **8.7 个 recall 点**。
> 更关键的是它**支配均匀 FP8**：用 **56% 的字节**拿到同档 recall。
>
> 主 kernel 的 MXFP4/MXFP8 UMMA 部分 **SM100 专属、仅分析**；indexer 打分用真实 SM90
> `fp8_fp4_mqa_logits` 锚定，量化语义与选择/下游 **架构无关**。目标卡代号敏感：全文用「目标卡」指代。

## 0. 结论先行

在真实 SM90 `fp8_fp4_mqa_logits` 锚定（max-abs-rel **2.722e-04**，与第 174 篇逐位一致）的 indexer
打分上（`T=256, C=65536, H=32, D=64, top-k=2048`，H100 sm90 实测）：

1. **均匀 MXFP4 的「2× 带宽」是有标价的**：KV 从 FP8 换 MXFP4，字节 **0.50×**、top-k recall
   **0.9616 → 0.8743**（翻转 79→258）——省一半字节换 **8.7 个 recall 点**。这就是「2× 带宽的
   排序精度代价」。
2. **两级级联几乎把它全补回来**：coarse 全 C 用 MXFP4、refine 只对**短名单 M**用 FP8，
   **M=2k（4096）时字节 0.5625×、recall 0.9612**——只比均匀 MXFP4 多 **12.5% 字节**，
   就回到 FP8 级（0.9616）。**M=4k 时 0.625×、recall 0.9616 与 FP8 逐位同档**。
3. **级联支配均匀 FP8**：用 **0.562× 的字节**拿到 FP8 级 recall（均匀 FP8 是 1.0×）。
   Pareto 图上级联点 `(0.5625, 0.9612)` 落在 `(1.0, 0.9616)` 的左上方。
4. **机制是「粗筛天花板」很高**：MXFP4 粗筛的 **recall@M** 在 M=2k 时已 **0.9978**（真 top-k 的
   99.78% 都在 MXFP4 的 2× 短名单里）；错失的只是**阈值附近那一小撮**被量化噪声挤出去的 KV，
   refine 一补即回（`ideal-refine` 用 fp32 重排 M=2k 得 0.9978，与天花板一致）。
5. **净收益斜率极大**：相对均匀 MXFP4，`dRecall/dBytes` 在 M=2k 时 **1.39**（每多 1.0× 字节换回
   1.39 recall 绝对量）；换 MXFP8 做 coarse（M=4k）只有 **0.164**，贵 **8.5×**。
6. **下游完全跟上**：`tau=0.25`（teacher 捕获质量 0.977）下，均匀 MXFP4 输出误差 `1.79e-2`、
   级联 `1.66e-2` = 均匀 FP8 的 `1.66e-2`（逐位同档）。

**一句话**：indexer 的 KV 精度不是「要么 8 位要么 4 位」的二选一——**用 4 位扫、8 位精读一小撮**，
在 0.56× 字节下拿到 8 位级的排序质量。

## 1. 定位：从「单级均匀精度」到「两级粗筛-精排」

第 174 篇的结论是「**KV 主导带宽、省位该省在 KV**」，并把问题表述成一张 `Q × KV` 精度矩阵——
但它的每一格都是**单级**的：全 C 个 KV 用同一种精度读一遍。第 171 篇量的 recall 翻转（FP8 70 /
MXFP4 306）也是在同一口径下。

真实的 indexer 打分是**两阶段的天然形态**：

```
stage 1 (coarse)：扫全上下文 C 个 KV，若用便宜精度（MXFP4）→ 读 C·bpe(MXFP4) 字节
stage 2 (refine)：只对 coarse 给的短名单 M（M ≥ k）用高精度（FP8）重算 → 读 M·bpe(FP8) 字节
总读取字节 = C·bpe(coarse) + M·bpe(refine)
```

它与「均匀低精」的区别只在**把省下来的字节花到哪里**：
均匀 MXFP4 把**全部** C 个 KV 降到 4 位（省 0.5× 字节，全量丢精度）；
级联**只把粗筛那遍**降到 4 位，**精读那遍读得少但读得准**（省 ~0.5× 字节，只对极少数 KV 丢精度）。

这不是新算法——**两级检索（recall + rerank）** 是检索系统的标准做法。本篇只是把它接到
indexer 的**打分算子精度**上，并量出「排序质量 vs 带宽」的 Pareto。这类问题
（coarse-to-fine、多级缓存/渐进精度）在访存受限算子上很常见，但前面各篇从未在 indexer 上拆过。

## 2. 实验设置

- **indexer 打分**：真实 SM90 `fp8_fp4_mqa_logits`（`attention.hpp:67-134` / `:124-130`），
  `q=(fp8, None)`、`kv=(fp8, 逐 token fp32 sf)`、`weights` fp32；与纯 torch 复刻对拍 max-abs-rel。
- **量化档**（纯 torch 复刻，`deep_gemm/utils/math.py` 语义；MXFP8/MXFP4 是 SM100 专属、仅分析）：
  - `fp8`：Q 裸 e4m3；KV 逐 token 一个 fp32 scale（`per_custom_dims_cast_to_fp8` `:75-81`）。
  - `mxfp8`：逐 32 元素 e4m3 + UE8M0（`per_token_cast_to_fp8` `:26-49`）。
  - `mxfp4`：逐 32 元素 E2M1（`per_token_cast_to_fp4` `:84-125`）+ UE8M0；`mxfp4_g16` 是逐 16。
- **字节模型 `bpe`（每 KV 元素读多少字节，含 scale 开销）**：
  `fp8 = 1 + 4/D`（逐 token fp32 scale）、`mxfp8 = 1 + 1/32`、`mxfp4 = 0.5 + 1/32`。
- **级联**：coarse 对全 C 算分 → 取 top-M 短名单 → 只把短名单位置的**高精分数**填回、其余 `-inf`
  → top-k。`bytes = C·bpe(coarse) + M·bpe(refine)`。
- **天花板 `recall@M`**：真 top-k 落在 coarse top-M 里的比例（级联的**上界**，refine 再好也超不过它）。
- **`ideal-refine`**：短名单内用 **fp32 teacher 分数**重排（理想 refine），验证「天花板 vs 实现」的差。
- **下游**：per-head softmax + GQA（`G=4`）共享支持集，`O[t,h,:]=Σ_{s∈S_t} P_h_renorm[t,s]·V[s,g(h)]`，
  温度 `tau` 扫描（第 172/174 篇同款语义）。

## 3. 结果

### 3.1 Part A：kernel 锚定

```
kernel vs torch-fp8 ref: max-abs-rel = 2.722e-04
teacher logit std = 31.8920, |logits|max = 227.471
```

与第 174 篇逐位一致（同 seed、同量化语义）——后续所有数字都在这块**真实算子**的量化地板上。

### 3.2 Part B：单级均匀基线（这就是「2× 带宽的代价」）

```
KV fmt       recall     flip       bytes/fp8
fp8          0.9616     79         1.0000
mxfp8        0.9602     82         0.9706
mxfp4        0.8743     258        0.5000
mxfp4_g16    0.8766     253        0.5294
```

- **FP8 → MXFP4**：字节 **0.50×**、recall **0.9616 → 0.8743**（掉 **8.7 点**）。
  这是「省一半带宽」的标价。
- **MXFP8 几乎免费**（0.9706×、recall 0.9602），与第 174 篇一致。
- **note**：`mxfp4_g16` 块更细（0.5294×）只把 recall 从 0.8743 抬到 0.8766（+0.23 点）——
  **块大小不是主杠杆**，精排才是。

### 3.3 Part C：两级级联

```
coarse           M      ceil@M    recall@k    bytes/fp8
mxfp4            2048   0.8743    0.8743      0.5312
mxfp4            4096   0.9978    0.9612      0.5625   <-- knee
mxfp4            8192   1.0000    0.9616      0.6250
mxfp4_g16        4096   0.9981    0.9613      0.5919
mxfp8            2048   0.9602    0.9602      1.0018
mxfp8            4096   1.0000    0.9616      1.0331
```

- **M=2k（4096）是膝点**：coarse MXFP4 + refine FP8，字节 **0.5625×**、recall **0.9612**
  （= FP8 的 0.9616，差 0.0004）。
- **天花板 `recall@M` 极高**：MXFP4 粗筛在 M=2k 时已含真 top-k 的 **99.78%**（0.9978）；
  M=4k 达 **100%**。所以级联的 recall 上限由「粗筛短名单」决定，而它**本来就很高**——
  错失的只是阈值附近被量化噪声挤出去的一小撮。
- **`ideal-refine` 印证**：短名单内用 fp32 重排 M=2k → 0.9978（= 天花板），M=4k → 1.0000；
  实现里用 FP8 refine（不是 fp32）得 0.9612（M=2k）——**掉的那 0.037 不是「短名单漏了」，
  而是 refine 自己也带 FP8 量化**（FP8 单级 recall 也就是 0.9616）。
- **coarse 用 MXFP8 是浪费**：它本身就 0.9602，做粗筛没有便宜可言（0.97×），
  级联反而抬到 1.0×——**粗筛必须真的便宜（4 位）才有意义**。

### 3.4 Part D：Pareto 与等字节对照

```
scheme                             bytes/fp8    recall
uniform/mxfp4                      0.5000       0.8743
cascade/mxfp4->fp8 M=2048          0.5312       0.8743
cascade/mxfp4->fp8 M=4096          0.5625       0.9612   <-- knee
uniform/mxfp8                      0.9706       0.9602
uniform/fp8                        1.0000       0.9616
cascade/mxfp8->fp8 M=4096          1.0331       0.9616
```

- **级联支配均匀 FP8**：`(0.5625, 0.9612)` 在 `(1.0, 0.9616)` 左上方——**56% 字节、同档 recall**。
- **与均匀 MXFP4 相比**：多 **0.0625× 字节**（12.5%）换回 **+0.0869 recall**（+8.7 点）。
- `M=k`（2048）的级联没用（refine 短名单就是 top-k 本身，等于没补）——**M 必须 > k**。

### 3.5 Part E：下游稀疏注意力输出误差

```
tau=0.25 (teacher 捕获质量=0.977):  uniform/fp8=1.66e-02  uniform/mxfp4=1.79e-02
                                    casc/mxfp4 M=4096=1.66e-02  casc/mxfp4 M=8192=1.66e-02
```

- 均匀 MXFP4 把输出误差从 `1.66e-2` 抬到 `1.79e-2`（复现第 174 篇 +18%）；
- **级联 `1.66e-2` 与均匀 FP8 逐位同档**（`1.66e-2`）——排序精度补回来了，下游就回来了。
- `tau` 越大（注意力越平、越依赖整段长尾）两者越接近，但级联始终 ≤ 均匀 MXFP4。

### 3.6 Part F：净收益标量

```
scheme                         bytes/fp8  recall     dRecall/dBytes
mxfp4 M=4096                   0.5625     0.9612     1.390
mxfp4 M=8192                   0.6250     0.9616     0.699
mxfp8 M=4096                   1.0331     0.9616     0.164
```

相对均匀 MXFP4，**M=2k 级联每多 1.0× 字节换回 1.39 recall 绝对量**；M=4k 递减到 0.699；
MXFP8 路径只有 0.164（贵 8.5×）。**收益集中在第一个 12.5% 的加价上。**

## 4. 三条「为什么」

1. **为什么粗筛天花板这么高（recall@2k = 0.9978）**：indexer 的打分是**密集、光滑**的
   （`|logits|max≈227`、`std≈32`），top-k 边界处的分数**密集且有间隔**；MXFP4 的量化噪声虽大，
   但只有**紧贴边界的那一小撮** KV 可能被挤出去——把短名单放大一倍（2k→4k）就把它们全兜进来。
   这正是第 171 篇「诊断量是阈值±σ 候选池、不是 margin」的直接推论：**候选池按 2× 放大即足够**。
2. **为什么「少读多精」比「全读低精」划算**：KV 字节在**粗筛那遍是 O(C)**、在**精排那遍是 O(M)**。
   把精排的 M 压到 `2k`（`M/C = 1/16`），精排的 8 位开销只有 `0.0625×`——**比粗筛省下的
   `0.5×` 小一个数量级**。于是同样的 `~0.5×` 预算，级联把「精度」只花在**排序真正相关**的
   `1/16` KV 上，而均匀 MXFP4 把损失**摊到全部 KV**。一句话：**该省的地方省、该花的地方花**。
3. **为什么 refine 用 FP8 而不是 fp32 就到顶**：FP8 单级 recall 本身是 0.9616——**量化噪声地板**。
   refine 只要达到 FP8 档就够，不需要 fp32；`ideal-refine`（fp32）与 FP8-refine 的差
   （0.9978 vs 0.9612）正好是「短名单是否包含真 top-k」与「refine 自身量化」两层。
   再往上（fp32 refine）收益被短名单天花板封顶——**refine 精度不必超过粗筛短名单的召回。**

## 6. 结论与边界

- **结论**：indexer 的 KV 精度是一个 **Pareto**，不是一个点。**均匀 MXFP4** 用 0.50× 字节换
  8.7 个 recall 点；**两级级联**（粗筛 MXFP4 全 C + 精排 FP8 仅 2k 短名单）用 **0.5625× 字节**
  把 recall 拉回 **FP8 级（0.9612 vs 0.9616）**、下游输出误差回到 `1.66e-2`。它同时**支配均匀 FP8**
  （56% 字节、同档 recall）。**收益全在第一个 12.5% 的加价**（`dRecall/dBytes`=1.39）。
  实务准则：**KV 用低精扫、用高精精读 top-2k 短名单；不要全量低精、也不要全量高精。**
- **边界 1**：字节账算的是**每 query 读多少 KV**（indexer 访存受限，字节就是时间）。粗筛与精排
  需要 KV **以两种精度可取**——实现上或存一份 MXFP4 粗副本 + 一份 FP8（存储是另一笔账），
  或从 FP8 的高位/低秩 view 近似出粗筛（bit-plane 类做法）。本篇量的是**读带宽**，未含短名单
  gather 的随机访问开销（`M/C=1/16`，量级小）。
- **边界 2**：本机 H100（sm90）只能跑 **fp8 档**真实 kernel（`attention.hpp:124-130`）；
  MXFP8/MXFP4 是 SM100 专属，用纯 torch 复刻（`math.py` 语义）分析，**仅分析**；主 kernel 的
  UMMA/UTCCP 部分未在本机执行。粗筛的「两遍扫描」在真实 kernel 里是否值得（多一趟 launch/KV 驻留），
  需 SM100 上端到端确认——但**读字节**这个下界是架构无关的。
- **边界 3**：`M=2k` 这个膝点依赖 `C=65536, k=2048`（`M/C=1/16`）与打分的分数间隔；`C` 越大、
  `M/C` 越小，级联越划算。下游用随机 `V`、`ρ=0.98` 参数化，是**结构性的**而非真训练权重。
