== 头文件解析（~/github/DeepGEMM/deep_gemm/include/deep_gemm/layout/mega_mhc.cuh）==
  kNumRoutes=4 kNumHCOutputs=24 BLOCK_M=64 BLOCK_N=24 BLOCK_K=64 kNumWarpsPerWG=4

== 真实形状（DeepSeek 量级 H=7168 hc=4 D=28672 T=4096 splits=16）==
  atoms=H/UMMA_K=896  k_blocks=H/BLOCK_K=112  atoms/k-block=8
  num_m_blocks=64  num_tasks=num_m_blocks*splits=1024
  每个 Post worker 的原子数 = 448（两 worker 各半）；每 lane 覆盖 4 浮点对/行/原子
  每 lane 每行 每 route 累加 3584 floats；×4 routes = 14336 floats/行（一个 worker）
  逐行归约路径：4-lane(row-group) 内 `warp_reduce_sum<4>` → 写 smem[worker][row] → 两 worker 相加
  （每行由 2 worker × 4 lane = 8 lane 负责，与 device A 对拍一致）

== TMEM 列预算（整块 512 列）==
  每 A stage 列=32 accum 起点=128 前向 used=176 -> 256
  反向 G0 累加器 u0[64,24] used=24 -> 32
  两者之和 288 <= 512: OK
  dz[T,D] = 28672 floats/行 远超 512 列 -> 只能按 K-chunk 流式（同前向 A stage 的 per-k-block 粒度）

== 「G0 累加器直喂 K1」 vs 「落 global scratch 再读回」==
  前向 WG3 的 gemm_partial = num_m_blocks*splits*BLOCK_M*NOUT = 1572864 elems = 6.291 MB
  省掉的往返（写+读）= 12.583 MB  （相对 dfn=688128 elems=2.753 MB 很小）
  => 「直喂」的主要收益不是省字节，而是**省掉 num_tasks 次 global round-trip 的延迟**（每 task 一个 split 的 24 列累加器，跨 WG 同步后立刻被同 CTA 的 K1 消费）。

== K1（含 G1a 折入）元素级算术强度 ==
  read=1059.7 MB write=118.2 MB flops~880.8 MFLOP -> AI=0.75 FLOP/B
  H100 HBM 实测可达 ~3.3 TB/s，FP32 峰值 ~67 TFLOPS -> 拐点 ~20 FLOP/B；AI=0.75 -> 访存受限

== 结论 ==
  1) 前向 Post 网格（2 worker × 每行 4 lane、4-lane 归约）在 device 上与 host double 一致（rel 5e-8）；
     用 32-lane 全 warp 归约会引入 rel ~2.47 的**结构性错误**（不是数值误差）。
  2) TMEM 预算：前向 256 列 + G0 累加器 32 列 = 288 < 512，单 kernel 内共存可行。
  3) K1+G1a 是访存受限的元素级段，与第 131/132 篇的六段账一致；目标卡上应复用前向 Post/Normal worker。
