# code-dive — 深读源码仓库并产出分析文章

## 触发场景

用户要求"精读/分析某个仓库或某组文件的实现，写成文章"。本流程是 Flash Attention 精读系列（2026-08）实践沉淀的方法论。

## 前置条件

- 目标仓库在本地（常见于 `~/github/<repo>`）。没有就先 clone——本机网络下 `git clone` 可能超时，备选：`codeload.github.com/<owner>/<repo>/tar.gz/<ref>`。
- 确认仓库当前 commit（`git -C <repo> rev-parse --short HEAD`），文章里引用代码用带 commit 的永久链接。

## 步骤

1. **选精读文件**：不贪多。每篇文章锚定 1~3 个核心文件（如 `flash_fwd_kernel.h`），其余只做上下文粗读。用 `wc -l` 和目录树先摸清规模。
2. **并行深读**：文件多/大时，派多个子 agent 分头精读，每个 agent 的任务书里写死：
   - 精读哪些文件（绝对路径），粗读哪些（仅用于对比）；
   - 输出格式要求：中文 Markdown 分析报告、行号引用必须真实（读文件确认）、数学用 LaTeX；
   - 重点维度：整体结构 → 数学/算法与代码的映射 → GPU/工程细节 → 测试与容差 → 精妙细节与坑清单。
   - 注意 API 限流：子 agent 失败（429）时错开重试，不要同时重启全部。
3. **定文章骨架**：把数学推导放最前，代码逐段对照放中间，工程权衡/对比表放最后。一个递推公式 ↔ 一段代码的映射是这类文章的主线。
4. **写作**：按 `write-post.md`。系列文章统一 slug 前缀 + 篇间 relref 互链 + 首篇放全系列目录。
5. **配套代码**：写一个纯 PyTorch（或最小依赖）参考实现到 `code/<slug>/`，含与 autograd/参考实现对拍的自测，实跑通过再提交。
6. **交叉核对**：文章里每个行号引用抽回源文件验证；agent 报告里的"结论性断言"（如"没有 online softmax"）抽一条人工复核，防止误报写进文章。

## 验收标准

- [ ] 所有行号引用属实（至少抽查 5 处）
- [ ] 每个"X 没有/不支持 Y"类否定断言都复核过
- [ ] 配套代码自测通过
- [ ] 文章能独立读懂：不看源码也能跟上推导，看源码能对上每一段

## 已知坑

- **不要直接照搬子 agent 报告**：报告是素材，文章要重新组织结构（报告按文件组织，文章按"数学主线"组织）。
- 子 agent 可能把别的实现的细节张冠李戴（尤其同仓库多版本并存时，如 FA2/FA3）——涉及"哪个版本有什么"的断言必须回到对应文件确认。
- 深读大文件前先看有没有生成物混入（`find ... -name "*.o" -o -path "*build*"` 排除）。
